# Toolkit 架构与改进方向

更新时间：2026-11-13。接口细节见 [PROTOCOL.md](PROTOCOL.md)、[INTERFACES.md](INTERFACES.md) 和[插件手册](plugin-dev/README.md)。旧评审放在 [archive](archive/README.md)。

## 模块边界

```text
主窗口                                    插件窗口
ctx.js：视图、UI、窗口所有权                pluginwin-host.js：窗口挂载、拖放、关闭
       └──────── plugin-sdk.js ────────────┘
                 公共插件能力与权限检查
                         │
                 protocol/hub.js
                 方案选择、请求与流登记
                         │
                 protocol/transports/*
                 invoke / Channel / event / stdio / PTY
                         │
Rust：命令入口 → 服务表 / provider 表 → 原生资源
```

`plugin-sdk.js` 不引用 Vue、全局外壳 store 或内置插件。两个窗口组合同一份公共能力；主窗口保留 `id`、`rpc` 的既有名称，插件窗口保留 `pluginId`、`request`。公共能力只在这里实现，不再两边各加一次。

视图与拖放路由属于窗口适配层。主窗口只向当前插件的视图投递拖放；独立窗口直接向自己的插件投递。它们不应该为了“统一”而增加一层通用路由器。

## 通用数据协议

**协议按数据访问语义设计。** 新增数据能力应围绕可复用的资源授权、区间读写、顺序传输、容量控制和取消来设计。校验和、图像处理、编辑器及播放器在服务或插件中组合这些能力。业务动作可以验证某条数据路径，其参数和算法留在业务层。主窗口与插件窗口共用公共 SDK。

单次载荷、在途字节、累计数据量分别计量。内存对象按其驻留大小预算。顺序流按在途块预算，消费者处理完一块后释放它，再允许下一块进入。随机访问资源按读写区间和缓存预算，文件总大小独立于 IPC 块大小。

| 现有路径 | 字节的存留与释放 |
|---|---|
| `rpc-raw` | 返回一次完整字节答复，适合大小可控的结果 |
| `binary.open` | 每次最多 256 KiB，单会话预留最多 16 MiB。写入追加到 Rust 缓冲区，`read` 复制区间供重复读取，关闭才释放会话 |
| `channel-raw` | 宿主可推送独立字节帧。消费方可以释放自己的引用，`send` 返回仅表示交给传输层，缺少消费确认和端到端流量控制 |
| Sidecar `stdio-line`、PTY | 已有专用的出队读取。Sidecar 按文本行传递，溢出可丢旧行。PTY 面向终端输出，两者的生命周期和错误语义由各自的传输定义 |

`ctx.fs` / `bridge.fs` 持有由原生选择器发放的文件引用，提供区间读取和分块保存。Rust 持有文件句柄，单块完成后释放缓冲。`ctx.files.pick/save` 与 `onDrop` 提供路径，Sidecar 以操作系统权限自行读写文件，宿主负责进程和消息生命周期。`ctx.files.sha256()` 保留原生增量计算入口。内存会话详情见 [BINARY-IPC.md](BINARY-IPC.md)。

### 通用文件与流的演进

- **文件资源。** 原生选择已发放可撤销的引用。现有区间读取可供大文本和二进制编辑器按视口加载，暂存写入可逐段生成修改后的文件。拖放后续接入原生授权。
- **顺序消费。** 增加有界的读写流。最小实现可以逐块拉取，消费完成后再读取下一块。推送模式按可用额度发送，消费完成后归还额度。约定确认代表的阶段、结束、取消、错误和重试语义。慢消费者测试应验证在途内存受预算约束，取消后原生文件句柄和队列会被回收。
- **媒体访问。** 复用获授权的文件资源，按需为播放器提供字节区间和正确的媒体类型。HTTP Range 可以支持跳转到文件的其他区间，播放仍需 WebView2 支持对应容器和编码。用大于内存会话上限的视频验证连续播放和跳转。[HTTP Range](https://www.rfc-editor.org/rfc/rfc9110.html#section-14)

文件读取可以通过逐块拉取实现顺序消费。消费确认的推送流和媒体入口是后续演进方向。

## 生命周期和资源归属

`plugins.js` 管加载目录与来源，`lifecycle.js` 管激活/停用，`disposer.js` 管插件取得的资源。外壳 `store.js` 是展示状态，不负责关闭原生资源。

资源有三层不同的记录：

| 层 | 记录什么 | 结束条件 |
|---|---|---|
| SDK cleanup scope | 插件拥有的订阅和流 | 停用、激活失败或窗口 dispose |
| JS hub | 当前窗口的协议句柄、回调和配对请求 | 终止帧或显式 `hub.close` |
| Rust session / PTY backend | 原生端点、停止回调、线程与句柄 | 原生退出、Stop 或宿主退出 |
| Rust `FileHandles` | 待选择的预约、已打开的文件和暂存写入 | 关闭、插件清理、页面重载、窗口销毁或宿主退出 |

这些记录各自服务于不同的生命周期，不能只删一个 Map 就当作全部关闭，也不应强行合成跨进程“大一统会话对象”。SDK 清理流时调用 `hub.close`；hub 再驱动对应传输停止原生端点。

本轮收敛了三个实际问题：

- 公共 SDK 只实现一次；服务权限、对话框参数、事件和流接口不再手工镜像。
- **发起资源获取时就登记清理**。停用期间尚未完成的流/订阅也会被等待和释放，而非在 `await` 返回后才尝试登记。
- 激活失败和正常停用共用 `releasePlugin`，释放热键、主题、scope、订阅与视图，清空上下文。失败后不留下半注册视图。

主窗口清理依旧逆序等待；窗口卸载采用并行发起清理，保证浏览器结束页面前已发出所有关闭请求。两者共用幂等的 `Disposer`，不是两套清理实现。

## 首屏与宿主启动

HTML 先请求主样式，`main.js` 只加载外壳依赖；Settings 为异步组件。外壳 DOM 挂载与 Vue 更新完成后直接显示窗口，再导入 `boot.js`、内置插件和完整组件词汇表。隐藏页面的 rAF 不再是显示前提，自检也按需导入。

`startup timing` 记录导航以来的入口、外壳、显示和宿主导入时刻，`boot timing` 保留 boot 内累计阶段。对外壳的静态依赖检查防止设置页或其他组件重新带入宿主内核；入口行为回归覆盖不派发动画帧和显示请求失败。分析和验证边界见 [启动分析](STARTUP-ANALYSIS.md)。

Tailwind 的源范围固定到前端 `src`，不随仓库新增的原生构建缓存、诊断文件或文档扩大。当前已复现默认范围误扫 `target-check` 导致十余秒生成 CSS；`startup CSS requests` 单独记录实际样式请求耗时，真实编译器回归检查源边界与布局规则。

## 原生执行边界

短时同步工作由命令提交到 blocking pool，持续 IO 用独立线程。`async fn` 本身不把同步操作变成异步 IO。

PTY 使用项目内的 `src-tauri/plugins/tauri-plugin-pty`：reader 只持管道，waiter 持子进程并在退出后关闭主端，随后回收 reader。前端流结束和原生资源回收是不同事件。详细原因和原生回归命令见 [冻结分析](FREEZE-ROOT-CAUSE.md)。

Rust 的进程级职责分为：

| 模块 | 职责 |
|---|---|
| `lib.rs` | 命令与服务表路由、启动编排、窗口及托盘入口 |
| `gateway_stats.rs` | 在途网关请求与执行阶段统计 |
| `ui_heartbeat.rs` | UI 活性、恢复阶梯、重建窗口与恢复后会话保留 |
| `forensics.rs` | 飞行记录、冻结快照与恢复验证 |

看门狗和网关统计使用独立模块，调用路径仍为 `crate::ui_heartbeat` / `crate::gateway_stats`，不增加包装接口或启动层。后续可将窗口管理与命令入口从 `lib.rs` 分开；模块迁移本身不改变 PTY 后端或解决运行时冻结。

网关统计给每个请求一张独立 ticket：完成时移除对应请求，最早请求完成后立即显示下一个存活请求；同名请求的阶段也分别更新。计数、最早请求与阶段由同一份短锁内的注册表读取。JSON 网关及其 blocking 任务共享 ticket，调用方取消时仍运行的原生工作继续被统计。

`gw.inFlight` / `gw.oldest` 覆盖 JSON RPC、raw RPC 和内存字节会话。流命令与 PTY 插件使用独立入口，判断冻结还需结合 beat/tbeat、原生 PTY 计数和日志。

## 进程管理职责

| 模块 | 职责 |
|---|---|
| `procman-supervisor.js` | 纯时钟规则、重启策略、参数规范化与显示文案 |
| `procman-scheduler.js` | 每次激活独立的定时与重启控制器，拥有全部 timer |
| `procman.js` | 运行会话、持久化与终端视图，向调度器传入当前配置和启动操作 |

调度器销毁后，尚未完成的启动及其 `.finally` 仍引用旧控制器，不能重新挂 timer；旧会话的退出帧也不会进入新激活实例的重启逻辑。控制器通过 `ctx.cleanup` 注册释放，正常停用和激活失败共用销毁路径。重启倒计时结束前重新读取配置，禁用或删除的 profile 不再启动。

会话在发起 PTY 请求前就带上本轮重试次数，退出帧先于启动 Promise 返回也不会绕过重试上限。运行历史以实际取得 PTY 句柄为准；创建失败保留上一次成功启动的时间，实际启动后快速非零退出仍记录该次启动。

## 信任边界

当前插件是宿主进程内加载的 JavaScript 模块，不是隔离沙箱。JS 权限检查用于及时报告调用错误；Rust 检查声明权限与路径，但插件身份仍是调用方提供的 id。共享主窗口的代码能接触宿主全局对象，不能据此声称能抵御恶意插件。

本轮不引入令牌体系或新的权限层。若将来要运行不可信插件，需要先明确执行上下文隔离和身份发放边界，而不是把函数名或隐藏全局对象当作隔离措施。现有分析保留在 [通信审计](COMMS-AUDIT-2026-09-23.md)。

## 存储并发与落盘

`storage.rs` 按规范化后的实际文件路径串行化一次请求中的读取与修改；同一插件的主窗口、独立窗口共享锁，不同插件的文件 IO 互不等待。路径规范化也覆盖 Windows 大小写别名。

写入使用同目录临时文件，写完并同步后原子替换 `data.json`，失败时保留旧文件并释放临时文件。只有文件不存在代表空数据；读取失败、损坏 JSON 和非对象根值返回 `io`，避免下一次修改静默覆盖原数据。`tempfile` 复用已在依赖树中的库，负责跨平台替换与临时文件生命周期。

这保证同一宿主进程内单次调用的完整性。连续 `get` → 修改 → `set` 仍不是事务；外部程序直接编辑文件或多个宿主进程共享目录也不受进程内锁保护。原子替换不等于断电耐久性保证。

| 优先级 | 问题与证据 | 建议 |
|---|---|---|
| 高 | 选择器已接通 `fs`，拖放仍交付路径 | 让原生拖放发放文件引用，按实际需求复用到媒体区间访问 |
| 中 | `procman.js` 仍包含运行会话、配置和终端 UI；定时器已独立 | 继续按会话控制与视图呈现拆开；保留已有纯规则与调度模块，避免再造插件内消息框架 |
| 中 | 内置 `store.js` 直接读取宿主 store，动态导入 `plugins.js`，是插件边界的实际例外 | 将安装/重扫管理能力收敛为宿主操作接口，再决定商店是否继续是插件 |
| 中 | `lib.rs` 仍聚合命令、窗口管理与托盘入口 | 看门狗与统计已独立；后续保持唯一网关与应用启动编排入口，整理窗口管理职责 |
| 低 | 多份文档重复维护数量和 API 表，测试为此解析源码格式 | SDK 改用真实构造对象检查；其他不容易枚举的事实只保留一个参考入口 |

表中列出仍可继续收敛的部分；已完成的 SDK、存储、统计与监测整理见上文。优先根据真实并发和运行日志推进；不为未来假设引入容器、通用插件基类或额外总线。

## 验证方式

- `npm test`：协议、公共 SDK、插件生命周期、窗口差异和文档链接。
- `npm run build`：主窗口和插件窗口均能构建，插件窗口不能引入整个主窗口内核。
- `cargo run --offline --manifest-path src-tauri/Cargo.toml --example host-checks`：原生纯逻辑检查。
- `cargo run --offline --manifest-path src-tauri/Cargo.toml --example pty-lifecycle-checks`：真实 ConPTY 生命周期检查。
- `cargo run --offline --manifest-path src-tauri/Cargo.toml --example storage-checks`：真实文件的并发读改写、异常数据保留及 Windows 替换失败检查。

测试应针对可见行为，例如“停用后没有遗留流”和“失败后没有视图”，而不是要求 SDK 必须写成某种对象字面量。服务/错误码等静态声明仍适合从源文件核对。

验证记录：原生存储检查、61 项 `host-checks` 和 Rust 应用构建已通过；样式扫描修复后 Node 全量 373 项、前端生产构建与 Vite 首次 CSS 转换检查通过。真实 WebView 冷启动耗时仍待新日志对照，阶段详情见 [开发记录](DEVELOPMENT-LOG.md)。
