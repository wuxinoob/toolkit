## 2026-11-05：进程调度归属与启动历史

### 阶段 1：激活实例拥有调度器

沿用 procman 的职责拆分待办，先检查实际定时逻辑。回归确认：计划启动还在等待 PTY 时停用插件，启动 Promise 完成后的 `.finally` 会重新挂定时器；旧实现随后又启动了第二个进程。

将定时和重启逻辑抽到 `procman-scheduler.js`，每次激活拥有独立控制器，销毁后不再挂 timer。旧会话的退出回调保留原控制器归属；恢复新实例不会把旧退出帧当成新的重启请求。控制器也登记到 `ctx.cleanup`，覆盖激活失败。重启倒计时结束时重新读取配置，已禁用或删除的 profile 不再启动。

验证：旧代码在停用回归中实际启动 2 次而不是预期 1 次；修复后调度及纯规则检查 39/39 通过，覆盖停用后的 pending spawn、旧帧跨激活、正常重启预算和禁用后的 pending restart。保留用户新增的 `output/` 等未提交内容，未发现正在运行的 Toolkit 或新的冻结日志。

下一步：`launchProfile` 的注释要求只记录成功启动，但目前失败后仍无条件写入 `lastRunAt`；先增加行为回归再修复。

### 阶段 2：启动失败保留历史

回归确认：PTY 启动抛出「program not found」后，原实现仍把历史时间和原因改成当前 autostart，并持久化为最近运行。现在只有取得 PTY 句柄才记录启动；原来的成功时间和原因在创建失败时保留。进程实际启动后快速以非零状态退出，仍会记录真实启动，避免把运行失败与创建失败混为一谈。

验证：新增创建失败保留历史、快速非零退出仍记录启动的两条回归；调度及纯规则检查 41/41 通过。

下一步：重启次数目前在等待 PTY 返回后才赋给新会话；若退出帧先于启动 Promise 完成，策略会再次按 0 次重试计算。下一阶段验证这种早退出时序与重试上限。

### 阶段 3：早退出仍遵守重试预算

回归确认：配置最多重试 2 次，若退出帧先于 PTY 启动 Promise 返回，旧实现每一轮都按 0 次重试计算，5 秒内实际启动 6 次，超过初始启动加两次重试的 3 次上限。

现在调度器把本轮重试次数传入启动操作，会话在请求 PTY 前完成初始化。去掉等待返回后再回填次数的逻辑，正常退出与早退出使用同一预算。
