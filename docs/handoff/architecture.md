## 1. 一句话概括

一个 Tauri（Rust）外壳 + Vue 前端的桌面工具箱。核心是一套**插件宿主**：插件是纯 JS 模块
（内置，或直接丢进一个插件目录的外部插件），可以画主窗口里的**视图**、也可以开**自己的独立窗口**，
能跑子进程（伪终端 / 旁路子进程）、读写自己的一份键值存储、收全局热键、读剪贴板、截屏、发系统通知。
**所有原生能力都经过同一个请求网关，权限默认拒绝。**

## 2. 技术栈与运行边界

| 层 | 技术 | 说明 |
|---|---|---|
| 原生外壳 | Rust + Tauri 2 | 进程、文件、窗口、托盘、全局热键、系统通知、截屏、剪贴板 |
| 前端 | Vue 3 + 组件库（Tailwind 系） | 主窗口外壳、设置页、插件视图 |
| 插件 | 纯 ES 模块 | 不 import 宿主模块，只用宿主注入的 API 对象 |
| 子进程 | 伪终端（ConPTY）/ 行协议子进程 | 由插件发起，宿主统一登记以便退出时清理 |

## 3. 四个执行体

| 执行体 | 是什么 | 里面跑什么 |
|---|---|---|
| **原生宿主** | 一个桌面应用进程 | 命令入口、服务层、权限表、会话登记 |
| **主窗口** | 一个页面（Vue 外壳 + 宿主内核 + 所有插件的视图） | 插件激活函数、视图渲染 |
| **插件窗口** | 每个窗口一个独立页面 | 同一个插件模块的"开窗"入口 |
| **子进程** | 插件启动的伪终端 / 旁路进程 | 用户要跑的任何程序；宿主只持句柄或进程号 |

主窗口与插件窗口是**两个页面、两个 JS 运行环境**：不共享内存，只共享同一套消息信封、
同一份冻结的协议契约、以及同一个网关。

## 4. 分层

```
插件代码（内置 / 外部）
   │  只使用宿主注入的 API（ctx / bridge），不 import 宿主模块
宿主内核        权限闸门 · 生命周期 · 视图注册 · 窗口 · 全局外壳状态
消息平面        方案表 → 各方案传输实现 → 统一信封 / 编解码 / 错误码
原生边界        一次 invoke 调用 · 推送通道 · 事件
原生宿主        命令入口 · 服务层 · 权限表 · 会话表
```

**唯一的主要抽象缝是"方案"（scheme）**：换一种通信机制 = 新增一个传输实现 + 它在方案表里的一行声明，
调用侧看到的仍是同一组"打开 / 发送 / 关闭"与同一套信封。

## 5. 通信协议

### 5.1 一条信封，七种 kind

```jsonc
{ "v": 1,
  "kind": "req" | "res" | "err" | "evt" | "data" | "end" | "exit",
  "id": 7,            // 请求/响应配对（仅请求-响应场景）
  "svc": "storage",   // 服务名（仅 req/res/err）
  "act": "get",       // 动作名
  "ch": "term1",      // 流通道（仅 data/end/exit/err）
  "p": { … } }        // 载荷：控制面是 JSON，数据面可以是原始字节
```

- 同一种形状在 **Rust 与 JS 各实现一份**，并有跨语言一致性测试；空字段不上线，往返字节稳定。
- **`err` 有两种含义**：带 `id` 的是某次请求失败的回复；不带 `id` 的是**流级失败**（终止这条流）。
  在双向载体上这个区分是硬要求。
- 三种编码：控制面用 JSON 信封，旁路进程用行式 JSON，数据面用"首字节表示类型的原始二进制"。

### 5.2 八个方案

| 方案 | 载体 · 编码 | 方向 | 能力 |
|---|---|---|---|
| `rpc` | 一次性调用 · JSON | 请求/响应 | 应答配对、保序 |
| `channel-in` | 批量调用 · JSON | ↑ 上行 | 上行推送（≤256 帧/批） |
| `channel-json` | 推送通道 · JSON | ↓ 下行 | 推送、保序、跨窗口 |
| `channel-raw` | 推送通道 · 原始二进制 | ↓ 下行 | 推送、二进制、保序、跨窗口 |
| `event-bus` | 事件 · JSON | 广播 | 跨窗口广播 |
| `in-process` | 直接函数调用 | 广播 | 同窗口内广播（零 IPC） |
| `stdio-line` | 子进程标准输入输出 · 行式 JSON | ↔ 双向 | 请求/响应 + 推送 |
| `pty-stream` | 伪终端 · 原始二进制 | ↔ 双向 | 推送、二进制、请求/响应 |

方案的能力（方向 / 是否保序 / 是否二进制 / 是否跨窗口）是一张**声明表**，传输实现与它分开。

**流提供者**（宿主侧的数据源，3 个）：定时器、一次性大块、剪贴板变化。
**上行接收端**（1 个）：把每一帧写成一行发给旁路进程的标准输入。

### 5.3 网关：十几条原生命令里只有一条是能力入口

```
插件 ──信封──► 网关命令 ──► 权限表核对（默认拒绝）──► 服务路由 ──► 动作校验 ──► 服务实现
```

| 类别 | 条数 | 说明 |
|---|---|---|
| **网关** | 1 | 唯一的能力入口，所有插件调用都走它 |
| 推送流开关 | 3 | 打开（两种编码）、关闭；除了通用流权限，还要提供者自己的权限 |
| 原生文件/消息框 | 1 | **自设权限闸门**（模态框会阻塞同步命令，所以它不能在网关里做） |
| 加载期引导 | 1 | 插件上报自己声明的权限 |
| 宿主内部维护 | 3 | 清理上一次前端遗留的会话、开机自启读写（仅主窗口可调） |
| 插件发现 | 4 | 扫描目录 / 单查 / 读入口 / 打开目录（只有宿主自己调，含路径逃逸防护） |

**两类闸门的区别是刻意的**：数据面的闸门在原生侧且默认拒绝（因为插件可以绕过注入的 API
直接调原生命令）；管理类操作只由宿主自己的代码调用，防的是"第二个前端上下文"而不是恶意插件。

**动作清单元数据也是权威的**：同一份服务/动作声明既用于网关校验，也用于向插件公布"这个宿主支持什么"，
所以两者不可能漂移。

### 5.4 服务与动作（9 个服务 / 36 个动作）

| 服务 | 动作数 | 说明 |
|---|---|---|
| `storage` | 4 | 每插件独立键值存储（整文件读写） |
| `host` | 8 | 自省（信息 / 常用目录 / 会话表 / 插件表 / 能力词表）、调试落盘；其中"按会话停止"和"撤销授权"仅宿主身份可调 |
| `proc` | 6 | 旁路子进程：启停、收发、列举 |
| `stream` | 8 | 流的生命周期、提供者列举、第三方进程的会话登记、上行写入 |
| `bus` | 1 | 跨窗口广播 |
| `hotkey` | 4 | 全局热键，由宿主代插件注册，按归属隔离 |
| `notify` | 1 | 操作系统通知（与站内提示是两回事） |
| `clipboard` | 2 | 文本剪贴板（**变化监听是流，不是动作**） |
| `screen` | 2 | 显示器枚举与截屏 |

### 5.5 权限

- 词表很小：**每个服务一个读/用权限字面量**（9 个）+ 一个对话框权限 + 一个窗口控制权限。
- 插件在清单里声明自己需要哪些；加载时上报给原生侧登记。**默认拒绝**，错误信息里会列出合法动作。
- 两道门：**原生侧是权威**（防绕过），**前端侧是体验**（早期、可读的失败）。
- 几个刻意的例外：订阅事件、读自己声明的热键、关闭自己打开的流**都不需要权限**（严格弱于"打开"）。

### 5.6 错误、超时、可观测

- **14 个错误码构成闭集**（拒绝、未知服务/动作、参数错、找不到、冲突、不支持、IO、启动失败、
  超时、传输、协议、编解码、内部），前后端各一份并由测试防止漂移；能力词表里也公布它们。
- 请求默认有 **45 秒超时**（可显式关闭）。**已知缺口**：超时只是调用方不再等待，宿主仍会把事情做完；
  真正的取消需要宿主侧协作，目前没有。
- 有一层**通信追踪**：可以打开后把每条收发写到诊断日志，用于回答"我的调用到底发出去了吗"。

### 5.7 流的两条边

- **下行**：宿主用推送通道把帧送进来，消费者拿到"帧回调 + 结束回调"。
- **上行**：宿主运行时提供的推送通道是**单向**的（前端只有接收方向），
  所以上行没有推送载体，只能用**批量调用**模拟（一批最多 256 帧），交给命名的接收端。
  **这是框架约束，不是设计偏好**，也是当前架构里最不"优雅"的一处。
- **流的结束语义**：帧序列最后必须有一个终止帧（结束 / 退出 / 失败），否则消费者会一直等。
  伪终端在子进程退出后不会立刻报告流结束（平台行为），所以有一个"排空窗口"（短暂静默或上限 1 秒）
  再发终止帧 —— 这是**有意的启发式**，不是精确判定。

## 6. 插件模型

### 6.1 两扇窗口，两套手工镜像的 API

同一个插件既能贡献**主窗口里的视图**，也能开**自己的窗口**，两处拿到的是同形的 API 对象
（主窗口侧习惯叫 `ctx`，窗口侧叫 `bridge`；`rpc`/`request`、`id`/`pluginId` 只是改名）。

| | 共享 | 只属于主窗口 | 只属于插件窗口 |
|---|---|---|---|
| 项数 | **27** | 4（组件工厂、窗口管理、注册视图、聚焦视图） | 4（窗口自己的名字、关闭自己、拖动自己、退场释放） |

**这 27 项必须两边都有**，历史上有若干项（文件选择、日志、关闭流、拖放）先在主窗口落地，
于是"同一段代码在另一种窗口里直接报未定义"——现在有专门的测试钉住这个对等关系，
任何单边新增都会失败。**一处刻意的形状差异**：拖放回调的第二个参数在视图里是"落在哪个视图"，
在窗口里是"窗口自己的名字"。

### 6.2 清单与来源

- 每个插件有清单（标识、名称、版本、入口文件、权限、贡献点：视图 / 热键 / 主题）。
  代码里也可以导出清单，**磁盘上的清单覆盖代码里的**。
- **内置插件**打进应用包，用户无法卸载，每次启动都要付出体积与启动成本；
  内置名单刻意保持极小（目前只有两个，用来覆盖"伪终端"和"四种流"两块没有别人覆盖的能力）。
  其余一律作为**外部插件**从插件目录加载。
- 两类的**行为完全一致**，区别只在"能否卸载 / 启动成本"。

### 6.3 插件窗口零样式

插件窗口的页面**不加载任何样式表**：设计令牌、通用类名、工具类在那边**都不存在，而且不会报错**
（元素就是没样式）。插件要自绘界面就得自带样式。这是刻意的取舍（"插件窗口应当完全独立"，
比"省掉一百多 KB 的工具类"更根本）。代价是：**同一段界面代码不能在视图与窗口之间直接搬**，
需要一份逐条的迁移对照。

### 6.4 生命周期

```
发现 → 加载（清单 + 入口） → 激活（上报权限 → 跑激活函数 → 注册视图 → 宿主代注册热键）
     → 停用（插件自己的销毁逻辑 + 宿主收集的清理函数一次性释放）
     → 重载 / 卸载
```

- 视图渲染是**可重复调用的纯函数**：切页、主题变化都会重新渲染，**DOM 不保证存活**。
- 插件窗口关闭时会自动释放它开的所有流与清理函数（否则会留下跑着的子进程）。
- 有一层"目录对账"：以磁盘为准重新扫描，决定加载 / 重载 / 移除（内置与外置走同一条路）。

## 7. 状态模型

### 7.1 状态分布

| 状态 | 存在哪 | 生命周期 |
|---|---|---|
| 外壳 UI 状态（当前视图、插件列表、提示、设置） | 主窗口内的响应式单例 | 窗口存续 |
| 用户设置 | 浏览器本地存储 | 跨启动 |
| 权限与已授权插件 | 原生宿主内存 | 每次启动由加载期重新上报 |
| 会话表（伪终端 / 旁路进程 / 流） | 原生宿主内存 | 进程存续；退出或回收孤儿时清理 |
| 插件自有数据 | 宿主应用数据目录下每个插件一个目录、一个 JSON 键值文件 | 跨启动 |
| 插件代码簿记（内置表 / 外部扫描结果 / 内容摘要） | 主窗口内存 | 窗口存续 |

### 7.2 运行时数据布局（结构，不是路径）

```
宿主的应用数据目录
├── 诊断日志（追加写，有大小上限）
├── 外部插件目录（每个插件一个子目录：清单 + 入口文件）
└── 插件数据目录（每个插件一个子目录，里面一个 JSON 键值文件；宿主自己也有一个）

宿主在本地缓存目录里另有一份浏览器运行时 profile（缓存，不是数据）
```

### 7.3 宿主会话表

- **一张表装三种东西**（伪终端、旁路进程、流），每条登记一个"停止"闭包，退出时统一收；
- 对"进程属于别人"的情况（第三方终端插件、前端直接起的进程），宿主只拿到进程号，就按进程树杀 ——
  这是"退出不留孤儿进程"的兜底；
- **伪终端的句柄不是进程号**（提供者自己用计数器编号）。把句柄当进程号登记过一次，
  后果是退出时可能杀到无关进程 —— 现在这条差异被写在契约里；
- 前端整页重载会留下"前端没了、进程还在"的孤儿，启动时会主动回收并记录一行日志。

### 7.4 一个内置工具的会话语义（最近三个 bug 的规则来源）

它是唯一带"持久配置 + 多进程 + 终端"语义的插件，也是踩坑最多的地方：

- 有一份持久化的**配置**（要跑什么、怎么跑、何时跑），和一份**运行记录集合**（运行实例，
  每条指回它的配置；一次性的临时启动没有配置归属）。
- **停止会刻意保留运行记录**（让用户还能回看输出），于是同一个配置**可能同时拥有多条记录**。围绕这点：
  1. **"这条配置的会话"不能取"第一条"** —— 第一条往往是已经结束的那条。规则改为：
     **活着（运行中/启动中）的优先；都不活时取最新**。修之前的表现很有代表性：
     停止后再点运行，行里仍显示"已停止"、键盘打不进字、再点运行只提示"已在运行"。
  2. **已结束的记录需要一个明确的丢弃点**：手动"运行"开始新一轮时丢掉该配置已结束的记录；
     定时 / 自启 / 重启**不丢**（那几条刻意不动用户的选择，删掉会让正在看的输出当场消失）。
  3. **"一个配置拥有几条记录"这个模型仍然没有正式定义** —— 现在靠两条纯函数补丁维持，
     见第 11 节。
- 还有一个通用的坑：**回放不是对话**。切页回来会新建终端并把历史回放写进去，
  新终端会把回放里的查询当成实时的去回答，于是往仍在运行的子进程里写进过期的转义序列。
  现在的规则是：回放期间静音终端的应答通道，并从回放里剥掉"会让终端回话"的序列。

### 7.5 伪终端/终端的四个平台陷阱

1. **重连 = 新建终端 + 回放文本**，而回放不是屏幕状态；全屏程序不能靠它恢复
   （现在靠"重连时触发一次全屏重绘"补偿，代价是每次切回来都多发一次无意义的尺寸设置）。
2. **子进程会发送"光标位置查询"并阻塞等待回答**；无界面消费者不会答，所以传输层在看门狗超时后补一个。
3. **输出结束不是流结束**：子进程退出后读取端仍可能挂着，所以要排空窗口（见 5.7）。
4. **响铃字节（BEL）由传输层吃掉并计数**：应用里没有任何东西能发声，所以它只可能是噪声；
   计数用于判断"这声是不是来自这条流"。**实测过一次"用户听到响声但计数不动"** ——
   说明那声不经过这条流（来自子进程或控制台宿主），别把计数当听感代理。

## 8. 界面分成三个世界

| 世界 | 用什么画 | 样式从哪来 |
|---|---|---|
| **外壳**（侧栏、设置页） | Vue 单文件组件 | 设计令牌 + 通用类名 + 工具类 |
| **插件视图**（主窗口内） | 宿主提供的组件工厂（在 Vue 之上，几百个组件导出） | 同上（同一文档） |
| **插件独立窗口** | 插件自己写原生 DOM | **什么都没有**（见 6.3） |

第三列是刻意的：插件窗口要能只靠一个 JS 文件活。代价是无法把视图代码直接搬到窗口里。

## 9. 启动顺序

```
安装调试句柄 → 挂通信追踪落盘 → 回收上一次前端遗留的会话 → 准备组件工厂
→ 注册通信方案 → 加载内置插件 → 扫描并加载外部插件 → 注册宿主自己的热键
→ 打印逐段耗时与逐插件状态 →（开发模式下再跑一遍应用内自检）
```

每一段都有耗时标记，是排查"启动慢"的第一现场；开发模式下还会跑一次覆盖底层契约的自检。

## 10. 已经被测试钉住的工程约束

这些不是风格偏好，改动时会直接红：

1. **一条网关**：插件只能通过网关触达原生能力；只有宿主自己的代码能调管理类命令。
2. **原生命令必须异步**，做 I/O 的还要进阻塞线程池。同步命令会占用"给所有窗口泵消息"的那条线程 ——
   症状不是"某个命令卡"，而是"整个界面卡"，所以这条被机器强制。
3. **枚举类事实由测试比对**：服务/动作数、方案表、权限名、插件能力对等表、界面组件词汇量。
4. **插件窗口零样式**（见 6.3）；不给插件界面引入新的运行时依赖。
5. **跨语言契约**（信封、错误码）前后端各一份，必须一致。

## 11. 已知的摩擦点（请重点评估这些）

> 下面给的是"现象 + 代价"，不含实现细节；每条都想知道：**该不该动、动了会连带什么。**

1. **一个内置工具插件同时承担五件事**：会话状态、持久配置、视图渲染、配置编辑对话框、
   终端渲染与重连。它也是踩坑最多的地方（见 7.4）。纯规则部分已经抽出去并有测试，
   但**主要的接线部分没有测试**（需要 DOM 与终端）。
2. **两套插件 API 是手工镜像的**（27 项共享 + 各 4 项独有）。现在靠两个测试防止漂移，
   但每次加能力都要在两处各写一遍 —— 这是"同一个能力在两种窗口里行为不同"这类 bug 的温床。
3. **"一个配置拥有几条运行记录"没有正式模型**（见 7.4）：
   现在靠"活着的优先 + 手动运行时丢已结束的"两条规则维持，语义上仍然模糊。
4. **终端消费侧的规则只存在于一个消费者里**（回放、重连、尺寸策略、应答静音、响铃计数），
   另一个做流演示的内置插件用的是另一套。
5. **枚举类事实散布在多处叙述性材料里**：改一个数字要同步若干处，靠测试事后抓。
   运行时其实已经有权威来源（能力词表），文档里的数字却是人写的。
6. **通信中枢一个类同时当路由器、流管理器、订阅/广播入口与追踪开关**；
   各方案的句柄形状大体相同但不完全一致（只有伪终端有句柄/进程号的概念，
   只有上行有批量发送）。
7. **界面三个世界没有共享的组件故事**（见第 8 节）：这是"零样式"决定的后果，
   但目前也没有一个"不依赖样式框架"的组件子集。
8. **原生侧的命令入口同时装着命令、能力装配、托盘、窗口握手、退出清理**；
   两个大服务各自带着队列与生命周期管理。
9. **权限字面量存在两份**（原生权威 + 前端闸门），靠测试比对两边。

## 12. 我特别想听建议的点

1. 分层是否合理？**通信中枢该不该拆成"路由 / 传输 / 观测"三层**，
   还是保持现在"一个中枢 + 一张方案表"的形状？
2. 两套插件 API：应该**生成**（一份表驱动两侧），还是合并成一个、由宿主按窗口能力裁剪？
   两种做法分别会牺牲什么？
3. 会话模型：一个"配置"与它的"运行实例"应该是什么关系？
   已结束记录的历史输出该归谁（配置、会话表、还是独立的日志/回放）？
4. 终端能力应该放在哪一层：框架级（方案表里的一等公民）、还是一个可复用的独立模块、
   还是继续"消费者各自实现"？
5. 原生侧怎么分模块而不破坏"所有命令异步 + I/O 进阻塞池"这条硬规则？
6. 文档/说明里那些可枚举的事实用什么机制做到单一来源（构建期生成？运行时下发的词表？）？
7. 插件独立窗口：要不要提供一套不依赖样式框架的组件子集，还是保持"完全自绘"？
   怎么判断哪种代价更小？
8. 现在的边界里，**哪些是历史妥协、哪些是真的约束**？请指出你认为最可疑的几条，
   以及如果只用一次重构来证明判断正确，你会先动哪一处。
