## 1. procman：三列布局 + 两个"新建"入口

### 实测

**列宽**：`grid-template-columns: 250px 1fr 270px`，默认窗口宽 1080px。

> **250 + 270 = 520px，占默认窗口宽度的 48%**，中间终端只剩约 560px。

**两个表单的字段对比**（这是你问的"是否冲突"）：

| "New session…"（左下，`<details>` 折叠） | "New / Edit profile"（左中） |
|---|---|
| name | name |
| program | program |
| args | args |
| cwd | cwd |
| ~~save as profile~~（勾选框） | env / cols / rows |
| | enabled / autoStart |
| | schedule（kind / at / every） |
| | restart（policy / maxRetries / delayMs） |
| **4 个字段** | **16 个字段** |

### 结论

**冲突，而且是结构性的**：上面 4 个字段是下面 16 个的**严格子集**，而"New session"表单
自己带了一个 **"save as profile" 勾选框** —— 也就是说**它已经能创建 profile 了**。
于是同一个 250px 窄列里，有两个入口都能新建 profile，字段还重叠。

概念上它们**不是**重复的（一个是"现在跑一次"，一个是"存成可复用的规格"），
但 UI 上完全没有把这条界线表达出来：都叫 new，都在同一列，字段还长得像。

**另外**：16 个字段的表单塞在 250px 宽的列里 —— 这是当前布局最难看的地方（见截图，
字段被压得很窄）。

### 可选项

| | 方案 | 代价 |
|---|---|---|
| **A** | **"save as profile" 改为交接**：快速表单保持 4 个字段；勾选后**打开完整编辑器并带上已填的值**。渐进披露，快速路径不变 | 小 |
| **B** | **合并成一个表单**：永远显示 16 个字段 + "save as profile" 开关 | 中（每次跑 `node --version` 都要面对 16 个字段，体验变差） |
| **C** | **只改文案**：快速表单改叫"Run a command"，profile 区改叫"Saved profiles"，并去掉快速表单里的勾选框 | 最小，但没解决"编辑器在 250px 里"的问题 |
| **D** | **编辑器搬出左列**：放进 Dialog（已有 dialog 组件），或放到中间区。左列只留列表 | 中 |

**我的倾向：A + D。** A 解决"两个入口都能建 profile"的冲突，D 解决"16 字段挤在
250px"的问题。两者独立，可以只做一个。

### 三列本身

左列在**做三件事**（会话列表 / profile 列表 + 编辑器 / 新建表单），右列**基本是只读信息**
（status、program、pid、uptime、bytes、output ring）+ 2 个按钮。

| | 方案 | 代价 |
|---|---|---|
| **A** | **右列变成中间区的一个 Tab**：中间已有 per-session 的 tab 条，"Terminal \| Detail" 很自然。省下 270px | 中（要改 tab 模型） |
| **B** | **右列可折叠**，状态记在 localStorage | 小 |
| **C** | **响应式**：窗口窄于某阈值时右列自动变成 tab | 中 |
| **D** | **不动** | 0 |

**我的倾向：A 或 C。** 右列的信息是"当前会话的详情"，而中间区已经是"当前会话"的
语境，把详情放成第二个 tab 比常驻 270px 更合理。

## 2. 自定义窗口栏

### 实测

- `tauri.conf.json` 的窗口配置**没有** `decorations` 字段 → 用原生窗口栏
- Rust 侧**没有** `WebviewWindowBuilder`；所有窗口（含插件窗口）都由 JS 创建：
  `new WebviewWindow(label, options)`（`src/host/ctx.js:200`）
- 当前 capability **缺**三个权限：`allow-minimize`、`allow-toggle-maximize`、`allow-start-dragging`

### 官方做法（Tauri v2）

1. `tauri.conf.json` 里 `decorations: false`
2. capability 加 `core:window:allow-{minimize,toggle-maximize,start-dragging}`
3. 拖拽：`data-tauri-drag-region` —— **只对直接标注的元素生效，子元素要各自标注**
4. Windows 上额外加 `app-region: drag`（触摸/笔输入需要）
5. 按钮：`getCurrentWindow().minimize() / toggleMaximize() / close()`
6. 双击最大化要手动实现（`e.detail === 2` → `toggleMaximize()`）

### 会失去什么

**确定会失去**（Windows）：
- **Snap Layouts** —— 鼠标悬停最大化按钮弹出的分屏布局选择器。它挂在原生标题栏上，
  自绘后没有了。这是重度用户会立刻察觉的功能
- **双击标题栏最大化** —— 需自己实现（几行，但容易漏）

**需要验证才能下结论**（我没有实测，标出来避免我替你做判断）：
- Aero Snap（拖到屏幕边缘吸附）—— `app-region: drag` 通常仍生效，但没验
- 窗口阴影 / Win11 圆角 —— 自绘后可能需要 `transparent: true` + CSS 自己画
- 无边框窗口的边缘缩放 —— Tauri 在 Windows 上一般有内建命中测试，但没验

### 成本

- 约 1 个组件（标题栏）+ 3 个权限 + 每窗口一个 `decorations` 选项
- **插件窗口要一并处理**，否则主窗口自绘、插件窗口还是原生，会更不一致

### 可选项

| | 方案 | 说明 |
|---|---|---|
| **A** | **只做主窗口**，插件窗口保持原生 | 不一致，但改动最小 |
| **B** | **主窗口 + 插件窗口都自绘** | 一致，但要给插件窗口也提供标题栏（插件自己渲染的话，等于又多一个契约） |
| **C** | **不做** | 保留 Snap Layouts 等系统集成 |

**我的倾向：先 B 里的"主窗口"部分**，即 A —— 但有个前提问题：**插件窗口的标题栏
归谁？** 如果宿主画，插件就少一块自由度（而它的窗口本来归它自己）；如果插件画，
就得在 `ctx` 上加一个 API。这个决定比"要不要自绘"更关键，建议先定它。

## 3. gallery 页最右侧的拖动条 + 左侧菜单跟着滚 —— **已找到根因并修复**

### 我一开始复现不了，因为我在浏览器里测

浏览器里（headless Edge 打 dev server）无论怎么测，**全页只有 `main` 一个滚动容器**。
但**在真实 app 里就复现了**。

### 怎么查出来的

给 app 打开 WebView2 的远程调试，直接在里面量：

```
WEBVIEW2_ADDITIONAL_BROWSER_ARGUMENTS=--remote-debugging-port=9222 npm run tauri dev
node scripts/app-eval.mjs "<表达式>"
```

实测（真实 app，gallery 页）：

| | 修复前 | 修复后 |
|---|---|---|
| 文档 scrollHeight | **4830** | **720** |
| 视口高度 | 720 | 720 |
| `main` scrollHeight | 9324 | 8582（正常滚动） |
| 侧栏 `top` | **-300（被顶出去了）** | **0** |
| `window.scrollY` | 300（能滚） | **0（滚不动）** |

### 根因

`main` 是 `overflow-auto`，但 **`position` 是 `static`**。

**CSS 规范：滚动容器只裁剪「以它为包含块」的绝对定位后代** —— 而成为包含块需要
`position` 非 `static`。所以插件视图里任何一个 `position: absolute` 元素
（reka-ui 的 slider / switch / 隐藏 label 里到处都是）**逃出了 `main` 的裁剪**，
转而以 `relative` 的根 div 为包含块定位，**把文档撑到了 4830px**。

于是：两个滚动条（`main` 一个、文档一个）+ 拖文档滚动条时侧栏跟着走。

### 修复

`src/App.vue` 的 `<main>` 加 `relative`（一行）：

```html
<main class="relative min-w-0 flex-1 overflow-auto p-3.5">
```

实测生效（HMR 后直接在 app 里复量）：文档 4830 → **720**，侧栏 `top` 恒为 **0**，
`window.scrollTo` **完全滚不动**。

已加回归守卫：`layout: the main scroll container is also a containing block`
（断言 `<main>` 同时有 `overflow-auto` 和 `relative`），已注入违规验证会变红。

**这不是设计取舍，是 bug，所以我直接修了。**

## 4. 配色 / 边框

### 实测

**边框对比度**（WCAG 相对亮度比）：

| | 值 |
|---|---|
| 深色主题 `--border` 在 card 上 | **1.26 : 1** |
| 深色主题 `--border` 在 canvas 上 | 1.36 : 1 |
| 浅色主题 `--border` 在 card 上 | 1.28 : 1 |
| 浅色主题 `--border` 在 canvas 上 | 1.18 : 1 |

参考：典型的"微妙分隔线"就在 1.2–1.5:1。**所以边框本身不刺眼。**

**边框数量**（gallery 页）：

```
463 个带边框的元素 —— 其中 378 个是"完整词汇表"里的 badge（outline 变体）
剩下约 85 个，其中 25 个是 card
```

### 所以问题多半不是"线太重"，而是"线太多 + 一种线干两份活"

**我找到的一个真问题**：

```css
--border: #262c38;   /* 区域分隔线 */
--input:  #262c38;   /* 控件轮廓 —— 和上面完全相同 */
```

**两个角色用了同一个值。** shadcn 上游把它们分开正是因为：

- **区域分隔线**应该很轻（越轻越好，只要能看出边界）
- **控件轮廓**应该更明确（否则输入框看不出是输入框）

现在它们绑在一起 → **调轻分隔线就会让输入框消失，调重输入框就会让分隔线变粗**。
这大概就是"线条视觉效果不佳"的根因：**你要同时满足两个相反的诉求，只能取中间值，
于是两头都不满意。**

> 注：`tests/plugins.test.mjs` 里有一条"同角色令牌保持同色"的测试把
> `--border` 和 `--input` 钉在一起了 —— 那是我之前的选择，**这条可以改**。

**另外**：gallery 页 25 张 card 堆叠，每张都有边框。`main` 还有 `p-3.5` 的外边距
→ **框套框**。这是"线太多"的主要来源（但 gallery 是演示页，密度天然高，
`notepad` / `floatwin` 那种 2–3 张 card 的页面观感要好得多）。

### 可选项

| | 方案 | 效果 |
|---|---|---|
| **A** | **拆开 `--border` / `--input`**：分隔线调轻（深色 → `#1e232d` 左右），控件轮廓保持或略强 | 直接解决"两头不满意" |
| **B** | 再加一个 `--border-subtle`，card 内部的线（`separator`、`card-footer` 上边）用它 | 层次更细，但令牌更多 |
| **C** | **card 去掉边框**，改用"表面色差 + 阴影"表达层级 | 需要把 `--card` 和 `--background` 的色差拉开（现在浅色下只有 1.05:1，几乎不可见） |
| **D** | 只在**演示密度高**的地方减线（gallery 的分区标题改成分隔线而不是 card 边框） | 改动局部，风险小 |

**已按 A 落地**（2026-09-21）：

| | 之前 | 现在 |
|---|---|---|
| 深色 `--border` | `#262c38` | `#1c212b`（更轻） |
| 深色 `--input` | `#262c38` | `#333b4a`（更明确） |
| 浅色 `--border` | `#dfe4ee` | `#e9edf4` |
| 浅色 `--input` | `#dfe4ee` | `#c8d1e0` |

两个令牌现在**各自独立**，所以将来单独调任意一个都不会牵动另一个。
`tests/plugins.test.mjs` 里"同角色令牌保持同色"那条已把 `--border` / `--input`
移出分组（并写明了原因）。

**B（再加 `--border-subtle`）和 C（card 去边框）没做** —— 它们是更大的改动，
建议看过实际观感后再定。对照页仍在：`style-options.html`，三个选项并排、深浅各一套。

## 5. native-select 展开的二级选项

### 实测（这条有定论）

```js
// 打开 native-select 前后
domNodesBefore: 1614
domNodesAfter:  1614
popupIsInTheDom: false
```

**展开后 DOM 节点数一个没变** —— 下拉弹层**根本不在 DOM 里**，它是浏览器/操作系统
在 DOM 之外画的。

组件本身（`NativeSelect.vue`）是：真实 `<select>` + `appearance-none` + 一个自绘的
chevron。所以**收起状态**（边框、圆角、箭头）是能美化的，**展开的选项列表不能** ——
没有任何 CSS 能碰到它。

`NativeSelectOption.vue` 给 `<option>` 设了 `bg-popover text-popover-foreground`，
但 **Chromium 在弹层里不理会这些**。

**所以这不是"没优化"，是平台硬限制。** 你的观察完全正确，而且 `select` 之所以没问题，
正是因为它是自绘的弹层（reka-ui popover），完全在 DOM 里、吃得到 token。

### 可选项

| | 方案 |
|---|---|
| **A** | **保留但在 gallery 里标注清楚**："真实 `<select>` —— 弹层由系统绘制，无法主题化；需要可主题化的下拉请用 `select`"。对比本身有教学价值 |
| **B** | **从 gallery 移除** `native-select`，只在文档里说明 |
| **C** | 文档里写清"什么时候必须用 native（`FormData` 读表单）"，gallery 保留 |

**我的倾向：A 或 C。** 这是"平台约束"而不是"我们的疏漏"，藏着不说反而更糟。
