### 三、main 侧修复（提交 `df50fce`）

按评审建议的优先级，做了不与该分支冲突的三项：

1. **`proc/kill_all` 实际一个进程都没杀**，却回报 `{"killed": N}`。
   根因：`kill_all_for` 先 `session::close`（remove 掉 Session，**连同 stop 闭包一起丢**），
   再 `stop_one` → 找不到记录返回 false，闭包永不执行；更早那轮还把 proc 注册表项
   remove（连 Child 一起丢）。
   **修法让错误顺序在结构上不可能**：`session::take_stop(plugin, ch) -> Option<StopFn>`
   —— 移除并把闭包**交还**调用方；`close()` 保持"只注销不停止"语义。
   `kill_all_for` 改为 take_stop 后执行，无会话记录时 `kill_handle` 兜底。
2. **kill 与 reader 抢同一把锁 → 可能永久阻塞**：`kill_handle` 需要 `Mutex<Child>`，
   而 reader 在 stdout EOF 后**持锁**阻塞在 `wait()`。sidecar 若关闭 stdout 却继续运行，
   所有 kill 路径（含退出时的 `session::kill_all()`）都会挂住。
   **修法**：`kill_handle` 改为**按 pid 杀**（复用 `session::pid_stop`，Windows 走
   `taskkill /T /F`），再用 `try_lock` 尽力回收 —— 杀完 reader 的 `wait()` 自然返回，
   由 reader 回收并发布退出码。
3. **Disposer 不等待异步清理**：`run()` 同步调用并丢弃 promise → 异步清理变
   fire-and-forget，资源可能在拆卸后才登记，rejection 变 unhandled。
   改为 await 每个清理 + 幂等（重复调用返回同一 promise），两处调用点改 await。

**验证（都在旧代码上确认会失败）**：
- 新增 3 项 Disposer 用例 → 旧 `run()` 上 **3 项全失败**。
- proc.rs 新增 2 项单测：kill_all 必须真的终止进程（5s 有界轮询，旧代码因进程仍在而失败）、
  close 后 stop_one 拿不到闭包（钉住陷阱）。
- host-checks 新增 3 项会话级断言（16 → **19 项全过**）。
- `node --test` **65 通过**、`cargo check --all-targets` 零警告、`npm run build` 通过。

## 六、插件热更新：Rescan 从"只发现"改为"对账"（提交 `f7a3748`）

原实现只做增量发现（`已有 id 直接跳过`），三个后果：**改完插件必须重启应用**、
**从磁盘删掉的插件永远留在内存**、**加载失败的插件因为行已存在而永不重试**。

现在是对账，五个分支：

| 磁盘状态 | 行为 |
|---|---|
| 新目录 | 加载 + 激活 |
| 摘要变化 | 先 deactivate 旧实例（释放热键/流/视图）→ 导入新内容 → 激活 |
| 摘要相同 | 完全不动（不重读、不重注册、不重复 toast） |
| 目录消失 | deactivate + 卸载 + 删行 + **撤销原生授权** |
| 加载失败 | 记住"失败的是哪份内容"，同内容不重试，内容一变就重试 |

关键设计点：
- **摘要放在原生侧**：`plugin_scan` 为每个插件返回内容摘要（FNV-1a 覆盖 plugin.json +
  入口文件），一次 no-op Rescan 只花一次调用。摘要必须**跨进程稳定** → 不能用
  `DefaultHasher`（无稳定性保证）。
- **重新加载不改变启用状态**：沿用持久化的 enabled，用户显式禁用的插件不会因为
  "丢了新字节进去"而被打开。
- **失败重试按内容而非按次数**：否则每次 Rescan 都重复同一个错误。

**顺带修掉的真实缺陷**：`registry::unregister` 此前**只有它自己的单测在调用** ——
插件从磁盘删除后原生授权永久保留，卸载过的插件仍被授权调用宿主。新增
`host/unregister`（**仅宿主身份可调**，插件不能撤销别人的授权）。

其他：Blob URL 用完即 revoke（此前每次重载泄漏一个）；Rescan 提示改为报告实际变化。

**测试**：`tests/external-reconcile.test.mjs`（4 项）驱动**真实**的
`scanExternalPlugins` + `loadPlugin` + 生命周期，只 mock Tauri 边界。
手法值得复用：**把 `URL.createObjectURL` 重定向到 `data:` URL**（并把 `Blob` 换成
能同步取到内容的替身），这样 Node 里也能真正 `import()` 插件源码，而不是 mock 掉
加载路径。另在 external.rs 加 2 项摘要测试。

接口清单随之更新：`host` 服务 5 → 6 个动作，总计 25 → 26（`docs/INTERFACES.md`）。

## 七、pty 生命周期：确定性信号取代 drain 启发式（提交 `ae21b7a`）

**根因不是"启发式不够好"，而是信号被依赖吞掉了。** 去看 `tauri-pty` 的 JS wrapper 才发现：
它的读循环以 `EOF` 错误结束，然后**静默 `return`**，而退出码在另一个 promise 上 ——
"输出结束"这件事对调用方**不可观测**，所以只能靠计时器猜（原来的 120ms/1.5s）。

改为**直接驱动插件自己的命令**（`plugin:pty|spawn/read/write/resize/kill/exitstatus`，
ACL 的 `pty:default` 已覆盖），顺序变成确定的：

```
spawn → session_open → read 直到输出结束 → exitstatus → exit 帧
```

三个关键点（都容易踩）：

1. **"输出结束"有三种拼法，是同一个事实**：Windows ConPTY 的 `read` 返回 0 字节 →
   `Err("EOF")`；**Unix 上 PTY master 在 slave 关闭后读到的是 EIO**（POSIX 把流结束
   报成错误而非 0）→ 不处理的话 Linux 上会误报为读失败；还有 `exitstatus` 已移除
   插件会话导致 read 查不到会话（`Unavailable pid`）。
2. **`exitstatus` 必须在输出结束之后再问**：Rust 侧它在 child 退出后**移除插件的会话**，
   提前问会让尚未取走缓冲输出的 `read` 查不到会话 → 立即退出的短命令**输出直接丢**。
   顺序化之后这个竞态在结构上不存在。（我第一版写成两个并发循环，就是踩了这个坑。）
3. **登记失败必须杀子进程**：原来 `session_open` 失败被 `catch` 掉 → 进程成为无人回收
   的孤儿。现在登记在读取之前，失败则 kill 并让 `open` 失败。

顺带：
- 去掉 pid 轮询（原来要等 2s 猜 wrapper 的异步初始化）—— `spawn` 直接返回 pid。
- `close()` 与 stdio 传输对齐：幂等、只发一个终止帧（`end`，因为是我们结束的，没有退出码）。
- **`tauri-pty` 这个 JS 包不再被引用，已从 `package.json` 移除** → 那条"它没有
  `main`/`exports`、必须写显式 dist 路径"的坑随之消失。

**测试**（`tests/pty-ordering.test.mjs`，6 项）：进程先退出时不得提前发 exit、
输出先结束时等退出码、三种"输出结束"拼法都要结束流而不是报错、登记失败要杀掉子进程、
close 幂等、以及**顺序处理完全不使用 drain 计时器**（直接断言 `setTimeout` 的 delay，
过滤掉 rpc 传输的 45s 超时）。
`navigator` 在 Node 里是 **getter-only**，测试里要 `Object.defineProperty` 覆盖而不能直接赋值。
