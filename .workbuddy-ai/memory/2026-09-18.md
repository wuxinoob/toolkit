### 三、main 侧修复（提交 `df50fce`）

按评审建议的优先级，做了不与该分支冲突的三项：

1. **`proc/kill_all` 实际一个进程都没杀**，却回报 `{"killed": N}`。
   根因：`kill_all_for` 先 `session::close`（remove 掉 Session，**连同 stop 闭包一起丢**），
   再 `stop_one` → 找不到记录返回 false，闭包永不执行；更早那轮还把 proc 注册表项
   remove（连 Child 一起丢）。
   **修法让错误顺序在结构上不可能**：`session::take_stop(plugin, ch) -> Option<StopFn>`
   —— 移除并把闭包**交还**调用方；`close()` 保持"只注销不停止"语义。
   `kill_all_for` 改为 take_stop 后执行，无会话记录时 `kill_handle` 兜底。
2. **kill 与 reader 抢同一把锁 → 可能永久阻塞**：`kill_handle` 需要 `Mutex<Child>`，
   而 reader 在 stdout EOF 后**持锁**阻塞在 `wait()`。sidecar 若关闭 stdout 却继续运行，
   所有 kill 路径（含退出时的 `session::kill_all()`）都会挂住。
   **修法**：`kill_handle` 改为**按 pid 杀**（复用 `session::pid_stop`，Windows 走
   `taskkill /T /F`），再用 `try_lock` 尽力回收 —— 杀完 reader 的 `wait()` 自然返回，
   由 reader 回收并发布退出码。
3. **Disposer 不等待异步清理**：`run()` 同步调用并丢弃 promise → 异步清理变
   fire-and-forget，资源可能在拆卸后才登记，rejection 变 unhandled。
   改为 await 每个清理 + 幂等（重复调用返回同一 promise），两处调用点改 await。

**验证（都在旧代码上确认会失败）**：
- 新增 3 项 Disposer 用例 → 旧 `run()` 上 **3 项全失败**。
- proc.rs 新增 2 项单测：kill_all 必须真的终止进程（5s 有界轮询，旧代码因进程仍在而失败）、
  close 后 stop_one 拿不到闭包（钉住陷阱）。
- host-checks 新增 3 项会话级断言（16 → **19 项全过**）。
- `node --test` **65 通过**、`cargo check --all-targets` 零警告、`npm run build` 通过。

## 六、插件热更新：Rescan 从"只发现"改为"对账"（提交 `f7a3748`）

原实现只做增量发现（`已有 id 直接跳过`），三个后果：**改完插件必须重启应用**、
**从磁盘删掉的插件永远留在内存**、**加载失败的插件因为行已存在而永不重试**。

现在是对账，五个分支：

| 磁盘状态 | 行为 |
|---|---|
| 新目录 | 加载 + 激活 |
| 摘要变化 | 先 deactivate 旧实例（释放热键/流/视图）→ 导入新内容 → 激活 |
| 摘要相同 | 完全不动（不重读、不重注册、不重复 toast） |
| 目录消失 | deactivate + 卸载 + 删行 + **撤销原生授权** |
| 加载失败 | 记住"失败的是哪份内容"，同内容不重试，内容一变就重试 |

关键设计点：
- **摘要放在原生侧**：`plugin_scan` 为每个插件返回内容摘要（FNV-1a 覆盖 plugin.json +
  入口文件），一次 no-op Rescan 只花一次调用。摘要必须**跨进程稳定** → 不能用
  `DefaultHasher`（无稳定性保证）。
- **重新加载不改变启用状态**：沿用持久化的 enabled，用户显式禁用的插件不会因为
  "丢了新字节进去"而被打开。
- **失败重试按内容而非按次数**：否则每次 Rescan 都重复同一个错误。

**顺带修掉的真实缺陷**：`registry::unregister` 此前**只有它自己的单测在调用** ——
插件从磁盘删除后原生授权永久保留，卸载过的插件仍被授权调用宿主。新增
`host/unregister`（**仅宿主身份可调**，插件不能撤销别人的授权）。

其他：Blob URL 用完即 revoke（此前每次重载泄漏一个）；Rescan 提示改为报告实际变化。

**测试**：`tests/external-reconcile.test.mjs`（4 项）驱动**真实**的
`scanExternalPlugins` + `loadPlugin` + 生命周期，只 mock Tauri 边界。
手法值得复用：**把 `URL.createObjectURL` 重定向到 `data:` URL**（并把 `Blob` 换成
能同步取到内容的替身），这样 Node 里也能真正 `import()` 插件源码，而不是 mock 掉
加载路径。另在 external.rs 加 2 项摘要测试。

接口清单随之更新：`host` 服务 5 → 6 个动作，总计 25 → 26（`docs/INTERFACES.md`）。

## 七、pty 生命周期：确定性信号取代 drain 启发式（提交 `ae21b7a`）

**根因不是"启发式不够好"，而是信号被依赖吞掉了。** 去看 `tauri-pty` 的 JS wrapper 才发现：
它的读循环以 `EOF` 错误结束，然后**静默 `return`**，而退出码在另一个 promise 上 ——
"输出结束"这件事对调用方**不可观测**，所以只能靠计时器猜（原来的 120ms/1.5s）。

改为**直接驱动插件自己的命令**（`plugin:pty|spawn/read/write/resize/kill/exitstatus`，
ACL 的 `pty:default` 已覆盖），顺序变成确定的：

```
spawn → session_open → read 直到输出结束 → exitstatus → exit 帧
```

三个关键点（都容易踩）：

1. **"输出结束"有三种拼法，是同一个事实**：Windows ConPTY 的 `read` 返回 0 字节 →
   `Err("EOF")`；**Unix 上 PTY master 在 slave 关闭后读到的是 EIO**（POSIX 把流结束
   报成错误而非 0）→ 不处理的话 Linux 上会误报为读失败；还有 `exitstatus` 已移除
   插件会话导致 read 查不到会话（`Unavailable pid`）。
2. **`exitstatus` 必须在输出结束之后再问**：Rust 侧它在 child 退出后**移除插件的会话**，
   提前问会让尚未取走缓冲输出的 `read` 查不到会话 → 立即退出的短命令**输出直接丢**。
   顺序化之后这个竞态在结构上不存在。（我第一版写成两个并发循环，就是踩了这个坑。）
3. **登记失败必须杀子进程**：原来 `session_open` 失败被 `catch` 掉 → 进程成为无人回收
   的孤儿。现在登记在读取之前，失败则 kill 并让 `open` 失败。

顺带：
- 去掉 pid 轮询（原来要等 2s 猜 wrapper 的异步初始化）—— `spawn` 直接返回 pid。
- `close()` 与 stdio 传输对齐：幂等、只发一个终止帧（`end`，因为是我们结束的，没有退出码）。
- **`tauri-pty` 这个 JS 包不再被引用，已从 `package.json` 移除** → 那条"它没有
  `main`/`exports`、必须写显式 dist 路径"的坑随之消失。

**测试**（`tests/pty-ordering.test.mjs`，6 项）：进程先退出时不得提前发 exit、
输出先结束时等退出码、三种"输出结束"拼法都要结束流而不是报错、登记失败要杀掉子进程、
close 幂等、以及**顺序处理完全不使用 drain 计时器**（直接断言 `setTimeout` 的 delay，
过滤掉 rpc 传输的 45s 超时）。
`navigator` 在 Node 里是 **getter-only**，测试里要 `Object.defineProperty` 覆盖而不能直接赋值。

## 八、P0 两项完成（提交 `bdb93e7` 错误码闭集、`e46e731` 上行流）

### 错误码闭集（14 个码）

原来只有 `denied`/`transport`/`protocol`/`codec`/`timeout` 稳定，服务失败报 `{svc}/{act}`
（只说明"哪个动作失败"，不说明**种类**）。我自己在 pty 传输里被迫匹配依赖的措辞
（`"EOF"`/`"Unavailable pid"`）——这就是没有闭集的代价。

- `protocol/codes.rs` 定义 14 个码；`protocol/codes.js` 是镜像；
  **`tests/codes.test.mjs` 解析两个语言的文件并比对**（重复声明只有被检查才可接受）。
- `Result<Value, String>` → `Result<Value, ServiceError>`（六个 dispatch + 可达辅助函数）。
- **关键坑**：编译器**抓不到**经 `From` 静默变成 `internal` 的点 —— `?` 作用在
  `Result<_, String>`、`Err("...".into())`、`ok_or("...")` 都会静默通过。这类点约 25 处，
  必须单独枚举并逐个定性，否则改完"看起来能编译"，实际全成了无信息的 internal。
- 边界：插件自己的后端可定义自己的码（calc 回 `div_by_zero`）；**流命令**的失败是
  invoke rejection 而非 err 信封，那条路径仍是普通字符串（代码里注明原因）。

### 上行流（`channel-in`）

**发现了一个框架事实**：Tauri 的 `Channel` 是**单向的** —— JS 侧只有接收回调，
**根本没有 `send`**（`@tauri-apps/api` 的 Channel 类只有构造器/onmessage/toJSON）。
所以框架**不提供**插件→宿主的推送载体。

因此上行流的载体是**批量 invoke**，并把这个取舍写进代码注释与文档，而不是假装是 Channel：
- `ctx.uplink(ch, {sink})` → 句柄与其它流同形（`send`/`close`）+ `sendBatch`；
  `send` 就是"批量为 1"。
- 帧逐个校验后交给**命名的宿主侧 sink**（表驱动，加 sink = 加表项）；首个 sink 是 `proc`
  （每帧一行 line-json 送到 sidecar stdin）。sink 名单由 `host/schema` 公布。
- 批上限 256 帧（一个批就是一次 IPC 载荷，没上限只是把内存问题搬家）。
- 权限沿用 `rpc:stream`；新增 `Capability.UPLINK` 与 `TransportKind.INVOKE_BATCH`。
- 测试里有一条专门证明**能力声明为真**：`channel-in` 声明 `uplink` 而非 `push`，
  所以用默认需要 `push` 的 `hub.stream()` 去开它会在**装配期**失败。

顺带修掉：文档里还留着早已移除的 `channel-json: backpressure` 声明；`protocol.test.mjs`
有一个**重复的测试**；boot/protocol 里硬编码的"7 个方案"改为从注册表推导（加方案不该
让测试变红），probe 改为断言"它依赖的方案都在"而不是总数。

## 九、应用内自检抓到我自己的两个 pty 缺陷（提交 `42cf32b`）

用户第一次跑起 GUI，启动日志直接给出证据：

```
FAIL t10-pty-session-tracked (8051ms): expected exit frame, got undefined
FAIL t11-session-registry: session leaked: [... "ch":"selftest-pty" ... "pid":0 ...]
```

### 缺陷 1：我的 pty 重写在真机上死锁（单元测试没发现）

第一版设计是**顺序**的：`read 到输出结束 → 再问 exitstatus`。真机上**输出标记收到了，
但终止帧永远没来**。根因：

> **Windows 上 ConPTY 的 reader 在子进程退出后不返回 0（EOF），它会一直挂着** ——
> 伪控制台只在 master 被 drop 时才关闭。所以"等 EOF"永远等不到，exitstatus 也就永远
> 不会被问 → 死锁。

旧实现没事，是因为它的 exit 帧来自 `onExit`（另一个 promise），**从不依赖 EOF**。

**为什么单元测试没抓到**：我把 `read` 的 mock 写成了"返回数据、再抛 EOF" —— 正好模拟了
平台**没有**的行为。**教训：mock 一个平台行为前，先确认真机是不是那样。**

修正：读循环与 exitstatus **并发**观察，按优先级：① 读循环自己结束 → 精确无等待；
② 否则进程消失后等数据流静默（120ms，上限 1000ms）→ **仍是启发式**，如实标注。
**"确定性"的说法收回** —— 能确定化的路径已确定化，剩下的是平台限制。

### 缺陷 2：把"会话句柄"当成了 OS pid（更早存在，更危险）

`spawn` 返回的是 **tauri-plugin-pty 自己的会话句柄**（`fetch_add` 计数器，从 0 开始），
**不是 OS pid**。旧代码把它当 pid 交给会话注册表 → **应用退出时会 `taskkill /PID <句柄>`，
可能杀掉一个毫不相关的进程**。日志里的 `"pid":0` 就是这个线索。
现在 pty 会话**不带 pid** 注册（宿主并不拥有这个进程，插件才拥有，停止走 `plugin:pty|kill`）。

## 十、Ctrl+C 退出：三条消息的解释 + 补上被跳过的清理（提交 `45e80fd`）

用户在终端 Ctrl+C 退出 `npm run tauri dev`，看到三条消息。逐条定性：

| 消息 | 性质 |
|---|---|
| `Failed to unregister class Chrome_WidgetWin_0. Error = 1411` | Chromium/WebView2 自己的关闭日志（1411 = ERROR_CLASS_DOES_NOT_EXIST）。**与 Ctrl+C 无关** —— 用 `timeout` 硬杀同样复现。纯噪音 |
| `exit code: 0xc000013a` | `STATUS_CONTROL_C_EXIT`，Windows 表示"被 Ctrl+C 结束"。cargo 把任何非零退出都写成 "didn't exit successfully"，这里只意味着"你打断了它" |
| `终止批处理操作吗(Y/N)?` | cmd.exe 在问要不要中止被中断的 npm 批处理，答 Y 即可 |

**但查出真缺口**：Tauri **不安装**控制台处理器（源码里搜不到 `SetConsoleCtrlHandler`），
所以 Ctrl+C 直接杀进程 → `RunEvent::Exit` **不触发** → `session::kill_all()` 不执行 →
当时若有活的 sidecar / pty 就会变孤儿。而 Ctrl+C 正是开发循环里最常见的退出方式。

**修法**：`run()` 里装控制台控制处理器（Ctrl+C / Ctrl+Break / 关闭控制台窗口），
先 drain 再自行 `exit(130)`（返回 FALSE 会让默认处理器在 drain 到一半时杀掉进程）。
依赖 `windows-sys`（早已是 tauri 的传递依赖，无额外构建成本）。

**刻意没做**：把退出码伪装成 0 让 cargo 闭嘴 —— 那会让脚本无法区分正常退出与被打断。
cargo 仍会打印一行非零退出，这是如实报告。

**顺带确认**：那次 Ctrl+C 之后没有孤儿（无残留 toolbox.exe / calc.exe；
32 个 msedgewebview2 无一属于本应用 —— 用 `user-data-dir` 分组核对过）。

## 十一、主窗口关不掉：ACL 静默拒绝（提交 `4dc8a4a`）

用户点右上角关闭按钮无反应。根因是 **capability 少了一条权限，调用被静默拒绝**：

Tauri 的 `onCloseRequested` 实现（`@tauri-apps/api/window.js`）：
```js
await handler(evt);
if (!evt.isPreventDefault()) await this.destroy();   // ← 用 destroy，不是 close
```
而 `core:window:default` 只授予 **28 项只读权限**（`allow-is-*`、位置、尺寸、监视器、
主题…），**既没有 `allow-close` 也没有 `allow-destroy`**。我们此前显式补了
`allow-close`（有人发现需要），却漏了 `allow-destroy` → destroy 被拒、异常在监听器里
被吞 → **窗口永远关不掉**。

**为什么"以前是好的"**：没有任何 `onCloseRequested` 监听器时，关闭走原生路径（不经
JS/ACL）；floatwin 注册监听器把关闭改成 JS 中介的 `destroy()`，才踩进 ACL。

**两处修改**：
1. `capabilities/default.json` 补 `core:window:allow-destroy`（description 里写明原因）。
2. `ctx.windows.onCloseRequested` 包 try/catch —— Tauri **只在处理函数成功返回后**才调
   destroy，所以插件的关闭回调一旦抛错，窗口就**永久关不掉**。插件有 bug 不该卡死窗口。

**新增 `tests/capabilities.test.mjs`（5 项）**：这类"JS 调了、ACL 拒了、错被吞了"的缺陷
其他测试都看不见，所以单独审计：扫描 JS 里的窗口 API → 映射权限 → 从**构建生成的
`acl-manifests.json`** 展开 `core:default` 得到实际授权集 → 逐一核对。

写这条审计时自己踩了两个坑（都加了守卫测试防"空转通过"）：
- `core:default`（2 段）与 `core:window:x`（≥3 段）的插件解析规则不同；
- **core 集合里的子项已是全限定名**（`core:event:default`），盲目加前缀会变成
  `core:core:event:default`，让整个展开**静默返回空** —— 审计会因此"全绿但什么也没查"。

已验证审计能抓到原缺陷（临时移除 allow-destroy → 第 1 项失败）。

## 十二、子进程管理 + 界面美化（提交 `f10333d`、`cdaa005`）

### 子进程管理：启动配置（profile）

session 是运行实例，**profile 是它持久化的描述**（跑什么、怎么跑、**什么时候跑**）：
- **start with app** 自启；**schedule**（`daily at HH:MM` / `every N minutes`）；
  **restart on exit**（never / on-failure / always + 重试预算 + 延迟）。
- 计划**从上次触发起算**，所以睡过一夜只跑一次而不是补跑一串。
- **用户手动停止不被重启策略撤销**；重试次数跨重启累加（否则长延迟的崩溃循环永远重启）。
- 停用插件时**清掉所有定时器**。
- 规则放 `src/plugins/procman-supervisor.js`（**纯函数**：时钟算术 / 重启策略 / env 解析 /
  默认值归一化），procman.js 只管定时器、持久化与 UI。
- 顺带修掉：`env` 之前在 pty.js 被硬编码 `{}`、ctx/hub 也没转发 → 现在全程透传。

**审计强化**：`tests/plugins.test.mjs` 原本只读插件入口文件，插件拆多文件后能力使用会
"半隐形"（检查照样绿、只是查得更少）。现在 `collectSource` 跟随相对 import 递归收集。

### 界面美化：为什么是 CSS 而不是组件库

**决定性约束**：外部插件是 Blob URL 单文件 ESM，**无法 import 任何东西** → JS 组件库
永远到不了它们。三种方案的实际覆盖：

| 方案 | 外壳 | 内置插件 | 外部插件 |
|---|---|---|---|
| Vue 组件库 | ✓ | ✓（打包） | **✗** |
| Tailwind 工具类 | ✓ | ✓ | **✗**（只生成扫描到的类） |
| **全局 CSS 类** | ✓ | ✓ | **✓** |

所以设计系统 = `@theme` 令牌 + `@layer components` 的 `.tb-*`（`src/assets/app.css`）。
**HeroUI 官方只有 React**（文档 /docs/react/）；shadcn-vue 是成熟 Vue 方案，而 shadcn 的
观感本就来自 token 层 —— 复现的正是那一层。Tailwind 作为工具类供外壳/内置插件用。

**只做深色**：应用一直是深色，而打不开窗口看效果的浅色主题等于盲发；令牌那一段就是
浅色主题需要覆盖的全部面积。

**overlay 容器刻意不用 absolute、不设 pointer-events:none**：前者会让空容器吞掉整个
应用的点击，后者会被子元素继承、让 overlay 上的按钮永远点不动。插件自己定位。

新增 `docs/UI.md`。已改造 `App.vue` + `SettingsView.vue`；内置插件视图尚未迁移。
