## 接口统一性核查 + 新增 probe 示例插件

用户四个问题：协议是否统一 / 新插件能否直接复用接口 / 接口清单 / 改进空间。
结论写入 **`docs/INTERFACES.md`**（含清单、映射表、例外、路线图、环境问题附录）。

### 核查结论
- **插件侧 100% 统一**：无插件 import Tauri、直接 invoke 或自己 new Channel（`tests/plugins.test.mjs` 强制）。
- **宿主侧 8 个原生命令**，其中 4 个在网关之外：`plugin_stream_open{,_raw}` / `plugin_stream_close`（必须携带 Channel）与 `plugin_register`（加载期引导）；另 3 个是宿主自身的插件发现操作（`plugin_scan` / `plugin_read_entry` / `plugin_open_dir`），插件调用不到。
- **5 服务 / 20 动作 / 7 方案 / 2 流提供者**。功能×接口映射由源码扫描生成（见文档 §5）。

### 核查中修掉的两处不实声明
1. **`plugin_registry` 是死命令** —— 注册了但**没有任何调用方**（Settings 走网关 `host/plugins`）。删除，字段并入 `host/plugins`，原生命令 9 → 8。
2. **`channel-json` 声明了 `backpressure`** —— 无实现、无消费方。移除声明并写明原因：*调用方无法依赖的声明比不声明更糟*。

### 新增 `examples/plugins/probe`（Plane Probe）
不 import 任何模块、不碰 Tauri API，只用 `ctx.*` + `ctx.protocol`，在 `activate()` 里跑 9 项接口检查（rpc / storage / 方案表 / 会话表 / channel-json / channel-raw / event-bus / in-process / 权限闸口）。**任一失败即抛错 → 启动日志显示 error 而非 active，日志本身就是结论。**

验证：`tests/plugin-interfaces.test.mjs` 用**真实** `buildCtx` + 真实 hub/transports 加载真实插件源码跑 `activate()`，只在 `invoke` 边界打桩；断言 9 项全过、权限恰好 4 个、视图按同一契约注册。

### 约定新增
- 测试静态审计支持 `// audit-ignore-next-line` 标记，用于插件里的**故意负向测试**（probe 用它测权限闸口）。
- `devUrl` 由 `http://localhost:1420` 改为 `http://127.0.0.1:1420`，与 `vite.config.js` 实际绑定的地址一致，不再依赖 `localhost` 在 webview 进程里的解析。

### 遗留的改进项（已列入 docs/INTERFACES.md §8）
- **P0**：上行没有推送通道（下行有 Channel，上行只有 req/res，插件无法向宿主推流）；错误码没有闭集（只有 4 个协议级码稳定，服务错误是 `{svc}/{act}` 字符串）。
- **P1**：`ctx.events.on` 同步 vs `ctx.bus.subscribe` 异步（方案抽象在 API 层泄漏）；`ctx.protocol` 在 `ctx.js` 与 `pluginwin-host.js` 各复制一份；**插件无法声明全局热键**（原设计 `contributes.hotkeys` 未实现）。
- **P2**：`rpc` 无超时/取消；无 schema 内省（不知道某服务有哪些 action）；版本协商只有"不匹配就拒绝"。

## 环境问题：本机 WebView2 不再为本应用创建渲染进程（非代码）

**症状**：`toolbox.exe` 启动、`RunEvent::Ready` 触发、WebView2 数据目录被创建，但页面脚本从不执行 → `debug.log` 不生成。

**排查手法（可复用）**：
1. Rust 侧临时 `eprintln!` 探针（`run()` / `plugin_rpc`）→ 确认 `run()` 与 `Ready` 到达，但 `plugin_rpc` 一次都没被调用。
2. 用 `webview.eval()` 让 JS **把结果写进 `document.title`**，再由 Rust `w.title()` 读回 —— 用非 IPC 通道观测 JS 是否真的执行（注意：`document.title` 不一定会同步到原生窗口标题，所以这条只能作辅助证据）。
3. 延迟 8s 后再 eval 一段"轮询 `__TAURI_INTERNALS__` 存在就 invoke"的脚本 → 仍无任何调用。
4. `tasklist` 比对：本应用启动前后 `msedgewebview2` 进程数不变（25 → 25），且那 25 个全部属于其它程序（QuickClipboard / Clash Verge / cc-switch / SearchHost）→ **本应用根本没产生渲染进程**。

**已排除**：前端（Vite 正常服务全部模块、`npm run build` 通过）；配置（换 `devUrl`、换全新 identifier / 全新 WebView2 配置目录均无效）；残留进程（无一属于本应用）；代码（同一二进制此前跑通过 15/15，`cargo test` 39 + `node --test` 42 全绿）。

**结论与建议**：本机 WebView2 运行时状态问题。依次尝试：重启机器 → 修复/重装 WebView2 Evergreen Runtime → 再跑 `npm run tauri dev` 看 `%APPDATA%\com.tan18.toolbox\debug.log`（应为 15/15）。

**教训**：`wmic` 被安全策略禁用；PowerShell 工具在本环境**不返回 stdout**，需要让它把结果 `Out-File` 到文件再读。

## P1 + P2 全部完成（用户要求：P0 不影响架构层面，先跳过）

### P1-1 统一事件 API 形状（消除方案抽象泄漏）
- 原来 `ctx.events.on` 同步、`ctx.bus.subscribe` 异步 → **方案会泄漏到每个调用点**。
- 现在 `subscribe` / `once` / `publish` 在**所有方案上都是异步**，`ctx.events` 与 `ctx.bus` 只差默认方案；底层统一为 `hub.subscribe/publish(…, { scheme })`。
- 配套：`hub.once()` 新增；`ctx.onSettingsChanged` 变为异步；所有插件调用点改为 `await`。
- **约定**：新增 API 时，方案差异只能体现在"默认值"上，不能体现在"形状"上。

### P1-2 协议契约去重
- 抽成 `src/protocol/contract.js`（`protocolContract()`），`ctx.js` 与 `pluginwin-host.js` 共用并 `Object.freeze`。

### P1-3 全局热键（原设计 `contributes.hotkeys` 一直没实现）
- 新增 `hotkey` 服务：`register` / `unregister` / `unregister_all` / `list`。
- **宿主代插件注册**：manifest 的 `contributes.hotkeys` 就是声明，插件不需要额外权限；注册在 `plugin.activate()` **之前**完成（否则插件无法在自己的激活流程里依赖它 —— 这个顺序 bug 被 probe 的检查抓到）。
- 按键以普通 `evt` 信封投递到 `hotkey:<action>`，`svc` 带 owner 以便区分同名 action；插件侧用 `ctx.onHotkey(action, fn)`。
- **只有宿主能指定 `owner`**（Rust `resolve_owner` 校验），插件不能替别的插件注册；冲突只告警不致命。

### P2-4 rpc 超时
- `ctx.rpc(..., { timeoutMs })`，默认 45s，`0` 表示不限；在**传输层**强制。
- 错误码 `timeout`，文案明确"调用方停止等待、宿主可能仍在执行、同步服务无法取消"。
- **不在信封加 `deadline` 字段**：同步网关无法兑现该承诺，加了就是假声明。

### P2-5 / P2-6 schema 内省即协商面
- `Service` trait 新增 `actions()`；网关**先校验动作再分发**，错误信息列出合法动作。
- `host/schema` + `ctx.schema()`：协议版本 / 服务与动作 / 流提供者 / 方案表（后两者由 hub 补上，Rust 不知道方案表）。
- **动作清单是权威的**：`schema()` 与网关校验共用同一份声明 → 不可能漂移。

### 顺带收紧的权限规则：观察不等于能力
- 订阅、读自己的热键、关闭自己开的流 → **不再需要权限**。
- 只有"发布到所有窗口 / 运行自带二进制 / 控制窗口"这类越出插件边界的动作才带权限。
- 权限表新增 `rpc:hotkey`（供插件查自己的热键）。

### 验证
`node --test` **60 通过**（新增超时、once、统一形状、schema、热键注册/释放、冲突不致命等用例）；`cargo check --all-targets` 零代码警告；`npm run build` 通过。

## 环境问题：example/test 二进制无法加载 —— **根因已找到并修掉**

- 现象：`cargo test` / `cargo run --example` 生成的二进制以 `STATUS_ENTRYPOINT_NOT_FOUND (0xc0000139)` 无法加载；`cargo build` 出的 app 二进制**能正常运行**。
- 对照排除：全新 `CARGO_TARGET_DIR` 同样失败（非缓存损坏）；hello-world 测试二进制正常（非"本机不能跑测试"）；失败二进制的 DLL 依赖是可用二进制的**子集**（非缺 DLL）；`crate-type` 改 rlib 无效。
- **根因**：tauri-build 把应用 manifest 编译成 `resource.lib`，并用 `cargo:rustc-link-arg-bins` **只链进 bin 目标**。没有 manifest 时 Windows 把进程绑定到 **comctl32 v5**，而代码导入的是 **v6** 符号 → 加载器在 `main` 之前失败。证据：可用二进制内嵌 `Common-Controls` 清单，失败二进制没有，但两者都导入 comctl32。
- **修复**：`build.rs` 在 `tauri_build::build()` 之后定位 `resource.lib`，转发给 `-examples`。两个坑：① cargo **没有** `-tests` 这个 link-arg 类型；② 通用 `cargo:rustc-link-arg` 也作用于 bin，而 bin 已链过同一份 .lib → 重复链接以 `LNK1123` 失败。
- **结果**：`cargo run --example host-checks` **16 项全过**（信封/编解码/服务表/schema 与表一致/hotkey 解析与 owner 委托/会话注册表）——本轮 P1/P2 第一次拿到可执行的 Rust 侧验证。`cargo test` 在本 crate 内仍不可用（cargo 限制），报告里要如实说明，不能暗示跑过。
- 本机 rustc 反复 ICE（增量缓存被杀软/文件锁损坏）→ `rm -rf target/debug/incremental` + `CARGO_INCREMENTAL=0` 可绕过。
