## ① 菜单与胶囊「长度不对齐」→ 根因是锚定错了边

`menuPos()` 原来 `x = clamp(S.pill.x, …)`，即**对齐左边缘**。但：

- 胶囊锚定在工作区**右上角**；
- 菜单（186 px）比胶囊（159 px）**宽**；
- 于是菜单右边缘越过屏幕边距 → clamp 把整体左推 → **两个边缘都对不上**。

改为锚定**共享右边缘**：`x = clamp(S.pill.x + pillSize().w - box.w, …)`。这既是"下拉菜单"的语义，
也是**唯一在胶囊宽度变化时仍成立**的对齐 —— 胶囊宽度是**实测**的，会随字号（`pillFontSize`）
与缩放（`pillScale`）移动，左对齐会每次都漂移同样的量。

菜单行数复核：`menuHtml()` 7 个 `.item`（rest / reset / extend / theme / recenter / config / stop），
README 里"seven rows"仍准确。

## ② 休息时「空闲检测 不可用」→ 三条插件侧根因（推理得出，非日志确认）

**逐项排除**（都是实测/读码，不是猜）：

- `idle.exe` 本身正常：`timeout 2 ./idle.exe` 逐行输出合法信封
  `{"v":1,"kind":"evt","ch":"ec-idle","topic":"idle","p":{"idleMs":N}}`；
- exe 解析正常：`resolve_exe_at` 是 canonicalize + prefix 检查，自检 t15 用 calc.exe 通过；
- 信封 `validate` 通过（`evt` 有 `topic`、有 `v`）；
- 默认 `pauseOnActive: true`，部署目录里的副本也能跑。

**真因无法从日志确认**，因为 **`ctx.log` 只是 `console.info/warn/error`**（`src/host/ctx.js:202-206`）
→ **不写 `debug.log`**。据此加固三处：

1. **重试预算永不归还** —— `retryIdle` 3 次失败后**永久放弃**，唯一复位点是改开关。一次瞬时失败
   会**毒化整个会话**。改为：成功采样时 `idleTries = 0`，且**每次进入新阶段都重置**。
2. **`hub.stream` 拒绝重复打开同一通道**（`throw ProtocolError.protocol('stream \`${key}\` is already open')`），
   而 `closeStream` 是**异步 IPC 往返** → 「关闭还没落地就重开」会撞上 already-open。
   新增 `S.idleClosing` 保存未完成的 close promise，`startIdle` 先 await 它。
3. **失败原因只进 webview console** → 用户看不到。新增 `S.idleWhy`，在视图里显示
   `空闲检测失败：<原因>`。缺失 exe / 权限被拒 / 通道冲突，从外面看是一模一样的。

顺带把 `idleBadge()` 改成**五态**：已关闭 / 待命 / 不可用 / 已离开·计时已重置 / 输入中·空闲。
原来把"待命"和"不可用"混在一起，正是这次难读的原因。

## ③ 工作时段空闲检测（新功能）

- 新开关 `pauseWorkWhenIdle`（默认 on）+ 新数值 `workIdleResetSec`（默认 300 s，10–3600，整数）。
- `syncWorkIdle()`：工作时段 `idleMs >= workIdleResetSec*1000` → **重置为完整时长并保持**
  （`setRemaining(workSec())` + `workIdlePaused = true`）；输入回来只**释放保持**。
- **语义刻意选"重置"而非"续计"**：长到能离开工位的时段不算工作，那一段挣来的休息也不该给。
  重置**只发生一次**（判定离开的那一刻），所以新周期实际从**回来的那一刻**起算。
- **`workIdlePaused` 必须是独立 flag，不能复用 `S.paused`** —— 暂停按钮是用户的决定，
  从"离开"回来不能静默取消用户主动按下的暂停。生效暂停 = 两者并集（`onTick` 的保持条件里 OR）。
- `wantsIdle()` 改为「**任一阶段读它就运行**」：`(rest && pauseOnActive) || (work && pauseWorkWhenIdle)`。
  好处是**阶段切换不再重启 helper** → 顺带消除了 ② 里的通道竞态。
- 两个配置面（菜单配置页 + 工具页）都由同一 `FIELDS`/`SWITCHES` 表生成，所以新项自动都出现；
  `saveConfig()` 成为**唯一的 syncIdle 汇聚点**。

## ④ 缩小分辨率后胶囊与透传按钮不重合 → 根因是 Windows 自己挪窗

链条：

1. `readArea()` 原来只在 `recover()`（休眠唤醒）与 `ensureRest()`（进休息）时调用；
2. 分辨率变化后 `S.area` 仍是**旧屏**尺寸；
3. `safePill` 按旧区域钳位 → 可能要求胶囊落在**新屏之外**；
4. **Windows 自己把越界窗口挪回屏内** → 插件的 `S.pill` 与窗口**实际位置脱钩**；
5. 锁窗（透传按钮）按 `S.pill + lockRect` 摆放 → 停在胶囊**以前**的位置。

修法两条路径合一：

- **`screenSig()`**：`window.screen` 六个数（width/height/availWidth/availHeight/**availLeft/availTop**）
  拼成签名。`availLeft/Top` 故意入签名 —— 任务栏换边只改工作区**原点**、不改尺寸，但足以移动所有窗口。
- **每 tick 比对签名**（`syncDisplay()`）—— 这是**唯一能抓到纯分辨率变化**的路径，因为
  `window.screen` **没有变化事件**；六次属性读，无 IPC。
- **`window` 的 `resize` 监听** —— DPI 缩放变化的**快路径**（它会让主窗口 resize，分辨率变化不会）。
- 响应统一为 `readArea()` → `safePill()` → `syncGeometry()`，即**一起重摆**胶囊 / 锁窗 / 菜单 / 遮罩。
- `activate()` 与 `recover()` 都要记录当前签名，否则下一次 tick 会把初始状态当成一次变化。

## ⑤ 单窗口自由切换鼠标透传：可行，但必须带外光标源 → 今天的两窗口更划算

**结论：单个窗口自己做不到。** `clickThrough` = `setIgnoreCursorEvents(true)`（`src/host/ctx.js:335`）
是**窗口级标志**，把窗口整个移出命中测试 → 透传窗口收不到**任何**鼠标事件（含 `pointermove`），
所以"关掉透传"的那个事件**不可能来自窗口内部**。Electron 有 `forward: true` 选项，**Tauri v2 未暴露**。

**唯一可行路径（带外光标源）**：

- 扩展 `idle.c` 加 `GetCursorPos`（今天只用了 `GetLastInputInfo` + `GetTickCount`）；
- 主窗口把**交互矩形**（屏幕坐标）推给 helper —— 它**已经算好了**：`S.pill` + `lockRect()`；
- **由 helper 做命中测试**，只发 **enter/leave 跳变** → IPC 从每帧 60 条降到**每次悬停 2 条**。

两个必须注意的点：

1. 翻转需要 **1 次 IPC 往返**，极快点击会落在空档 → 命中矩形要 **padding**；
2. `GetCursorPos` 是**物理像素**，而窗口摆放是**逻辑尺寸（DIP）** → 交换协议里要带缩放系数。

**真正的收益在"多个热区"**：三个按钮用今天的设计要**三个窗口**。一个热区不值得引入原生代码 + 竞态。
（已完整写进 README 的 Notes。）

## 文件访问：drop-in + 原生选择器落地（fs 读写推迟）

按用户裁定：**fs 读写不做**，只把 drop-in 和 dialog 做成插件可用的。

**关键技术点： 是同步命令 → 跑在主线程 → 在那里调
 会死锁**（对话框要主线程的消息循环来泵，而我们正占着它）。
dialog 插件自己的命令都是 `async fn` 就是为了这个。
所以新增了 **async 原生命令 `plugin_dialog`**，用与网关相同的
`host::registry::is_allowed(&plugin_id, "rpc:dialog")` 自闸。

**`dialog:*` 权限刻意不加进 capability** —— 插件 import 不到那个 JS 包，
但 `__TAURI_INTERNALS__` 存在；不加权限 ACL 就默认拒绝那条直接路径，
只剩受闸的入口。

**`ctx.onDrop` 不需要权限**，因为宿主**只把 drop 送给当时正在显示的那个视图** ——
用户拖到他看着的界面上。否则一个插件能静默收割本该给另一个插件的路径。
走 **in-process**（窗口本地，零 IPC），因为插件视图本来就在主窗口里。

**顺带发现一处不一致（未修）**：`event-bus` 回调收到**完整信封**，
`in-process` 收到**裸 payload** —— 与「方案差异只在默认值、不在形状」矛盾。
`ctx.onDrop` 走 in-process，所以让它直接回调 `(paths, info)` 把差异挡在插件外，
但这条不一致本身还在。

## 🔴 P0：权限闸可被伪造身份绕过（已报告，未修）

## 内置插件 vs 核心：一个容易混淆的区分

用户问「内置插件的删除会影响实际功能吗」「不应该是插件调用核心的 api 吗」。
**答案：内置插件就是插件，形状与外部插件完全一样** ——
两者都是 `export const manifest` + `activate(ctx)` + `ctx.*`。
差别只有**投递方式**：打包（`registry.js` 静态 import）vs drop-in（Blob URL）。

**所以删内置插件 = 移除一个功能，但不动核心。** 核心是
`host/` + `protocol/` + `components/`；`src/plugins/` 是**随包发布的插件**。
`registry.js` 的标题就是 "Built-in plugin registry" —— 它是一份**清单**，不是核心。

实际改动量：删一个内置插件 = 去掉 registry 的 import + 一条测试期望。
（`store.js`/`ctx.js` 里的 eyecare/floatwin 引用是**注释**和窗口 label，不是依赖。）

② Windows 操作中心真的弹出（到了系统）。只有 ① 说明系统拒绝了。

## 通信 trace 扩展到全部消息类型（rpc → 全类型）

**问题**：trace 只包 `hub.request`，所以只看得到 `rpc`。流在持续推帧、
事件走两个方案、`pty`/`sidecar` 是对话不是调用 —— 只听电话的一边。

**修法：包在 hub 的四个入口上，而不是 request 上。**
全部消息都汇进这四个方法：

| 入口 | 覆盖 |
|---|---|
| `request()` | `rpc` |
| `publish()` | `pub`（两个方案） |
| `subscribe()` | `sub` **+ 每一个到达的 `evt`** |
| `stream()` | `open` / **每一帧 `frame`** / `end` |

**`sidecar`/`pty`/`uplink`/`streamRaw` 全部走 `stream()`** —— 漏斗红利，不用单独包。

行形状：`rpc -> id svc/act 3ms ok` / `pub -> id scheme "topic" {preview}` /
`sub <- id scheme "topic"` / `evt <- id scheme "topic" {preview}` /
`open -> id scheme ch=x` / `frame <- id scheme ch=x 48B` / `end <- id scheme ch=x`。
`->` 发、`<-` 收。payload 截断 80 字符。

**`evt` vs `sub` 是这次最大的价值**：`sub` 只说明订上了，`evt` 才说明消息真的到了。
「订上了但收不到」和「根本没订上」是两类完全不同的 bug，没 trace 时长得一样。

**顺带修掉一个真 bug：观测者变成了参与者。** `trace()` 原来没兜异常 ——
测试里放一个会抛的 sink，异常从 `hub.subscribe` 传播出来**把订阅本身弄坏了**。
现在内部 try/catch。

**帧在 Node 里测不了**：`in-process` 没有 `open()`，所有有 `open()` 的方案都要 Rust 宿主。
那条测试只断言 wrap point 被到达，**注释里写明了**，免得以后以为它测了帧。

## 快捷键：声明 ≠ 注册（语义变更）

`contributes.hotkeys` 原来是**声明即注册**。现在它是**一个请求**：
宿主记录它（Settings 才有东西可列）但**不注册**，用户要在
**Settings → Hotkeys** 打开，键才到达操作系统。

**为什么**：装上就能占全局快捷键的插件，可以在**别的所有应用里**顶掉用户依赖的
快捷键，而用户从未同意。声明与注册分开，用户才有否决权。

首次见到声明时以插件给的 key 作初始值存下（`enabled: false`）——
Settings 有东西显示，默认**惰性**。用户改过后，**插件改默认值不覆盖它**。
绑定存在 `store.settings.hotkeys['<pluginId>:<action>']`。

**`ctx.onHotkey` 按 action 订阅，不认 key** —— 所以用户改键，插件代码零改动。

## 真 bug：共享视图容器让旧视图覆盖新视图

**症状**：切到别的页面，msglog 一出新行，当前页面被顶回 msglog。

**根因**：`ViewHost` 的容器**是同一个 DOM 元素**。切视图时宿主清空它并渲染新视图，
**但插件还握着那个元素**（msglog 的 `state.root`），下一行 trace 一来就
`render(state.root)` → **覆盖掉新视图**。看起来像「跳转」。

**这是宿主的问题，不是某个插件的** —— 任何有异步输出的插件都会中
（终端、日志面板、进度）。所以修在宿主：

    <div :key="viewId" ref="mountEl" ...>

**`:key` 让 Vue 在切换时丢弃旧节点** → 插件的陈旧引用指向**已脱离文档**的元素 →
写入仍然发生但**不可见**。插件不需要知道自己被卸载 ——
**这一点很重要：根本没有这种通知可以给它。**

watcher 要 `await nextTick()` 后再渲染（keyed 元素在 patch 之后才是新的）。

## `ctx.focusView(viewId)` —— 「热键启动插件」的完整实现

`ctx.onHotkey('open', () => ctx.focusView('main'))`。

- **只能切你自己的视图** —— 想切别人的表达不出来，这正是不用加权限的原因
- **不需要权限**：那是你自己的界面变得可见，用户看得见、点一下侧栏就能撤销
- **viewId 拼错会抛**，不静默（否则像「热键突然失效」）
- **做不到**：插件读不到 `store.activeViewId` → 「再按一次切走」写不出来

## 热键的两个边界（已核实，未改代码）

**问：插件没启动，热键能启动它吗？** —— 要分两种情况，答案相反：

- **插件已启用、只是视图不在前台 → 能。** 注册发生在 `activate()`，
  而处理函数走事件总线 —— **与哪个视图在前台无关**。
  配 `ctx.focusView` 就是完整的「热键召唤」。
- **插件被禁用（走不到 activate）→ 不能。** `registerHotkeys` 在 `activate()` 内部
  （lifecycle.js:242），禁用的插件根本到不了那里，**一个键都没注册**。

要支持第二种，需要：① 禁用的插件也注册（仅当用户已启用那个热键）；
② 宿主拦截热键事件，先 `activate` 再重新投递。**未实施**。

**问：热键能绑定到某个具体功能吗？** —— **能，而且现在就行。**

`action` 是任意字符串，插件自己映射到任意函数；Rust 侧
`remember()` 用 `Vec<String>` per plugin，**一个插件可以持有多个热键**。

    "hotkeys": [
      { "key": "ctrl+alt+1", "action": "open-notes" },
      { "key": "ctrl+alt+2", "action": "run-profile" }
    ]

    ctx.onHotkey('open-notes', () => showNotes());
    ctx.onHotkey('run-profile', () => runProfile('dev'));

**所以「按热键执行 procman 的某个 profile」今天就能写。**
