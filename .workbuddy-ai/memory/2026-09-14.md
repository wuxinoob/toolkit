## 在 toolbox 中落地"统一消息协议"（本轮主要工作）

按上面的设计，在**本仓库**（不碰 eyecare）重建了项目，核心是把"载体 × 编码"两轴显式化。

**协议核心**
- 统一信封 `{v,kind,id,ch,svc,act,topic,code,msg,p}`，7 种 kind（req/res/err/evt/data/end/exit），空字段不上线。
- 4 个编解码：`json-envelope` / `line-json` / `raw-binary`(1 字节 kind 前缀) / `object`。
- 7 个方案（transport × codec）登记在 `src/protocol/registry.js`，实现各一个文件在 `transports/`；`transports/index.js` 启动即断言"声明的方案都有实现"。
- **能力协商**：方案声明 capabilities（push/binary/crossWindow/…），功能声明需求，不匹配在装配期报错而非运行期特判。
- 三个原生入口全部查表：`plugin_rpc`（信封进/信封出）、`plugin_stream_open{,_raw}`（携带 Channel）、`plugin_register`。`lib.rs` 内**没有** `if service == ...`。

**关键设计决定**
- Rust 侧权限登记表（`host/registry.rs`）由 `plugin_register` 填充，**fail-closed**：未注册的插件 id 直接拒绝 → 绕过 `ctx` 直接 invoke 也拿不到权限。`__host__` 为宿主身份，隐式放行。
- 统一 `SessionRegistry`（`services/session.rs`）纳管 sidecar/stream/pty，退出只调一次 `kill_all()`；第三方插件拥有的进程用 `pid_stop` 按 pid 杀树 → **修掉了 eyecare 的 PTY 孤儿缺陷**。
- 跨窗口广播走网关 `bus/publish` → Rust `app.emit` → 各窗口 `listen`，替代 eyecare 的 250ms storage 轮询。
- `ctx.protocol` / `bridge.protocol` 把信封构造器交给插件——外部插件是 Blob URL 单文件 ESM，无法 import 协议模块。

**测试抓出的两个真实缺陷（已修）**
1. `pty-stream` 在 `await`（pid 轮询）之后才注册 `onData/onExit`，会丢掉进程启动时的首批输出 → 改为先注册回调再 await。
2. 在 `open` 期间就发出终止帧的流，`hub.stream` 仍会把句柄写回 `streams` → 永久残留。加 `settled` 标记后不再写回。

**验证**：`cargo test` 39 通过（含 examples/calc-plugin 真实 sidecar 端到端：6×7=42 与 div_by_zero 两条信封路径）；`node --test` 26 通过（7 种方案的一致性契约）；`cargo check --all-targets` 零警告；`npm run build` 通过；`cargo build` 链接出可执行文件。
**文档**：`docs/PROTOCOL.md`（协议参考）、`README.md`（总览）、`examples/{plugins/hello,calc-plugin}`（可投放的外部插件示例，calc.exe 已用 gcc 编译并纳入测试）。

之前只验证到"编译+单测通过"，没有真正跑起来过。补上了两条闭环：

- `src/host/boot.js` 现在把启动过程**自报**到 `{appData}/debug.log`（`--- boot ---` / `message plane:` / `boot ok:` / 每个插件状态 / `BOOT FAILED: <stack>`）。之前启动失败只进 webview console，外面什么都看不到——这是排查困难的主因。
- 新增 `tests/boot.test.mjs`：用 Tauri shim + `register()` 加载 `browser-stubs-loader.mjs`（stub 掉 CSS 与 `@xterm/*`）在 Node 里跑**真实 boot 路径**，断言 5 个内置插件全部 active、视图注册齐全、方案表已发布、权限都上报、以及"单个插件 activate 抛错不致命"。

**真实运行又抓到两个缺陷（已修）**
3. `pty-stream` 的 exit 帧会**抢在尾部输出之前**到达（tauri-pty 的 read 循环与 wait() 独立），把 `exit` 当终止的消费者会丢最后一段输出 → 实测 `t10` 拿不到 `cmd /c echo` 的回显。改为退出后等数据流静默 120ms（上限 1.5s）再发 exit。
4. 外部插件的权限有**两个来源**：`plugin.json`（宿主扫描用）与代码里的 `manifest`（注册时用），两者漂移后表现为莫名的 `lacks permission`。改为 **plugin.json 权威**（`mergeManifest`），并加审计断言两者必须一致。

**权限模型对齐**（一个能力一个权限）
- `stdio-line` → `rpc:proc`（运行插件自带的二进制是独立且更强的能力）；`channel-*`/`pty-stream` → `rpc:stream`；`event-bus` → `rpc:bus`；`in-process` 无。
- 会话生命周期（`session_open`/`session_close`）从 `host` 服务移到 `stream` 服务，使 `rpc:stream` 单独覆盖整个推送数据面（含 PTY）。
- `ctx.closeStream` **不加权限**：开启时已校验过，且只能关自己注册的流。
- `ctx.sessions()`（列表）仍在 `host` → `rpc:host`。

**外部插件默认启用**：新增 `adoptNewPlugin`，首次发现即启用（与"新内置插件默认启用"同一规则），显式禁用仍然持久 —— 之前复制进去 + Rescan 后是 inactive，与 README 承诺不符。

**最终验证**：应用内自检 **15/15 全绿**（含 t15 sidecar 真实往返 6×7=42 + div_by_zero）；7 个插件 active（5 内置 + 2 外部示例）、7 个视图；`cargo test` 39、`node --test` 39、`cargo check --all-targets` 零代码警告、`npm run build` 通过、二进制 `toolbox.exe`。
