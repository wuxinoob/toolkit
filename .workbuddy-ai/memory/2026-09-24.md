## 🔴 P0（性能）：主线程被同步命令阻塞 —— 12 个命令里 11 个是同步的

查「主窗口拖拽/滚轮卡顿、插件窗口也卡」。**答案就是用户猜的那个方向**。

**Tauri 把没有 `async` 关键字的命令跑在主线程上**（官方原文：*"Commands without the
async keyword are executed on the main thread unless defined with
`#[tauri::command(async)]`"*），而主线程是给**所有**窗口泵消息的那一条。所以阻塞它
卡的不是一个窗口，是整个应用。

**原本 12 个命令里 11 个是同步的** —— 包括 `plugin_rpc`（每个插件调用都过的网关）。
它背后的服务做的是阻塞文件 I/O：

| 动作 | 主线程上的阻塞 I/O |
|---|---|
| `storage/get` | `create_dir_all` + 读整个 store + JSON 解析（**每次调用，无缓存**） |
| `storage/set` | `create_dir_all` + 整个 store 重写 |
| `host/write_debug_log` | `metadata` + open + write + close，**每行一次** |
| `bus/publish` | `app.emit` 扇出到每一个窗口 |

`plugin_scan` 更重：遍历插件目录 + 读**每个插件的完整入口文件**（算 digest 要字节）——
这就是启动账里 `external 6183ms` 的来源，而且**每次开插件窗口都跑一遍**
（`pluginwin-host.js:163`）。

**有意思的是**：`lib.rs` 里 `plugin_dialog` 的注释**早就写过这个理由**
（"`plugin_rpc` is a *synchronous* command, so it runs on the main thread"），
但当时只是为了躲 `blocking_pick_file` 的死锁，**没有推及全局**。

**改法**：① 12/12 全改 `async fn`，规则统一（不逐条判断"够不够便宜"，因为失败模式
不可见）；② 做 I/O 的命令再套 `spawn_blocking` —— `async` 只把工作挪出主线程，
而阻塞调用会占住 runtime worker，**worker 数 = 核数**，一串 storage 调用会饿死其他
async 任务，那是同一个 bug 换顶帽子。权限闸口留在闭包**外面**。

## 同一轮挖出：自放大的窗口几何回路

`examples/plugins/eyecare/main.js` 胶囊窗口的 `resize` 处理器**每条 `WM_SIZE`** 跑一遍
`reportSize()` + `reportLockRect()`。**Windows 在拖拽/缩放期间是连续发 WM_SIZE 的**，
于是每一遍：

```
getBoundingClientRect() 强制同步布局 → publish（广播到每个窗口）
  → 主窗口 control('size') → plugin_rpc → 原生 SetWindowPos
  → 又产生一个 resize → 回到第一步
```

**跨两个窗口 + 原生侧的自放大回路**，同时占住插件窗口 JS 线程、主线程、所有窗口的
事件处理 —— 主窗口跟着卡，因为其中一样是全局的。

改成 rAF 合并（`scheduleReports`）。**两层保护各管一件事，都要有**：rAF 挡住
"值还在变时跑得比有用更快"，`sizeReporter` 的去重挡住"值停了事件还在来"。
主题变化那条路径原本自带一个 rAF，也并进同一个合并器。

## 排查方法（可复用）

**「谁在阻塞主线程」的查法**：① 列出所有命令，看谁没有 `async`
（`grep -nE "^\s*(async )?fn (plugin_|host_)"`）；② 看这些命令背后的服务有没有
`fs::`；③ 查输入侧有没有按 OS 消息频率跑的 IPC（`resize` / `pointermove`）。

**「日志里 trace 是什么」**：`hub.js` 的 trace 走 **sink → 网关 → `write_debug_log`**，
所以**每条 trace 行本身就是一次主线程 rpc + 一次文件开关**。排查时先看它开没开
（`localStorage['toolbox.traceRpc']`），开着的日志量不能当负载证据。

## 🔴 空 ACL：一个会伪装成「前端插件全坏了」的构建状态

删除事故的**下游后果**，也是用户报的 bug。因果链：

1. 12:00 文件消失，**包括 `capabilities/{default,pluginwin}.json`**
2. 一个正在运行的 `tauri dev` 构建监听器**当即重建**，此时 capability 目录是空的
3. `tauri-build` 写出 **空 ACL**：`OUT_DIR/capabilities.json` = `{}`（**2 字节**）
4. 我恢复了源文件，**构建产物没有** —— 而 Cargo 缓存了它
5. 12:24 启动的应用用的是那份空 ACL → **每个窗口零权限**
   （`core:event:allow-listen`、`core:window:allow-get-all-windows`、`pty:allow-spawn`
   全被拒）→ 看起来就是「插件都不可用」

**关键认知**：Tauri **运行时不读** `capabilities/*.json`。`tauri-build` 把它们编译进
`OUT_DIR/capabilities.json`，`generate_context!` 再嵌进可执行文件，**Cargo 会缓存**。
所以**源文件正确 ≠ 跑起来的应用有权限**，而**所有既有测试读的都是源文件** ——
这个缺口没有任何东西在盯。

**判据**：`wc -c src-tauri/target/debug/build/toolbox-*/out/capabilities.json`
→ 正常上千字节，**`2` 就是 `{}`**。产物带时间戳，能对上是哪次构建干的。

**修**：`cargo clean -p toolbox` 然后重建。（先要**优雅关闭正在跑的应用**，
否则 `cargo clean` 报「拒绝访问 os error 5」、链接报 `LNK1104 cannot open toolbox.exe`。）

**已加守卫**：`tests/capabilities.test.mjs` 新增一条，把**编译出来的** ACL 与磁盘上的
`capabilities/*.json` 逐条对比（按 mtime 只要求「构建看得见的文件必须编译进去」）。
**实测过**：写入空 ACL → 测试失败并打印修复命令。
`docs/plugin-dev/debugging.md` 的「权限被拒」一节也补了这个失败模式。

## ❌ `win:self` 不可行 —— Tauri 的窗口命令**不校验调用者身份**

想给插件窗口一个「作用域限自己」的能力来消掉几何回路。**查完源码：做不到。**

`tauri-2.11.5/src/window/plugin.rs:13-21`：
```rust
fn get_window<R: Runtime>(window: Window<R>, label: Option<String>) -> crate::Result<Window<R>> {
  match label {
    Some(l) if !l.is_empty() => window.manager().get_window(&l)   // 按 label 取任意窗口
      .ok_or(crate::Error::WindowNotFound),
    _ => Ok(window),
  }
}
```
而 ACL 判定在 `webview/mod.rs:1458`：`resolve_access(&cmd_name, self.window().label(), ...)`
—— 按**调用窗口**授权，**目标窗口由调用者传的 `label` 决定，两者不匹配校验**。
window 插件的 156 个权限**都没有 `scope` 字段**。

**⇒ 把 `allow-set-size` 给 `plugin-*` 窗口，等于让每个插件窗口能操作任意窗口（含主窗口）**，
而且外部插件可以绕开 bridge 直接 `__TAURI_INTERNALS__.invoke('plugin:window|set_size', {label:'main'})`
—— 和当初 `global-shortcut:allow-unregister-all` 是同一类洞。**比现在更糟，不是等价交换。**

**真正能做的（安全的那一半）**：把「限自己」放到**宿主层**而不是 ACL 层 ——
`ctx.windows.control(label, …)` 是主窗口在执行，宿主知道是哪个插件在调，可以记录
`label → pluginId` 并做归属校验。**当前 `control` 没有归属校验**（插件 A 能改插件 B 的窗口），
这是真 bug，可修。而「让插件窗口动自己」的正解是 **`bridge.drag()`（原生拖拽，零 IPC）** ——
它已经可用。

## ✅ 开窗成本：两处与优化无关的浪费（`48c613e`）

**① 每个窗口都在解析编译整个外壳。** `main.js` 静态 `import App from './App.vue'`。
**实测**（走 `dist/assets/pluginwin-host-*.js` 传递闭包）：**782.3 KB / 24 chunks → 40.8 KB / 4 chunks**（19×）。
主窗口 534.9 KB 不变。

**机制要点（容易搞错）**：`pluginwin-host.js` **从来没有** import 过 `App.vue` ——
是**打包器**把两者链起来的（入口静态引入的模块落进一个 chunk，插件窗口那个动态 chunk
又共享了它）。**所以这个不变量必须在源文件层面检查「有没有静态 import」，走源图查不出来。**

**② 开窗要读遍插件目录。** `pluginwin-host.js` 调 `plugin_scan` 再 `.find()` ——
而 `plugin_scan` 为了算 digest 读**每个插件的完整入口文件**。本仓库 8 个插件、
入口合计 ~896 KB（`moment-notes` 一个 686 KB），全读一遍只为拿一个 `dir`。
新增 **`plugin_info(id)`**：只读 manifest（~300 字节）并命中即停。
返回**新的 `PluginInfo`**（无 `digest` 字段）而不是 `ExternalPlugin` ——
用空 digest 填一个没人要的字段正好是这个命令要避免的成本，且空值会被当成有效值。

`service-table` 检查停在 6 个服务，而 `notify` 是另一个会话加的**合法**第 7 个 →
harness 一直 26 通过 / 1 失败。**一个红的 harness 等于没人看的 harness。**

## 🔴 工具行为：沙箱会**重跑**命令（重要）

做「回退-测量-恢复」时踩到：`cp src/main.js /tmp/x.js && python 改文件` 这条命令
**执行了两次** —— 第二次的 `cp` 把**已改过**的文件当成了备份，替换也做了两遍
（产生重复 `import App`）。**之前 `git commit` 打印「nothing to commit」也是同一个原因**
（第一次已提交，重跑时无事可做）。

**推论**：① 判断副作用是否成功**只看最终状态**（`git log`、文件内容），不看命令输出；
② **别在一条命令里做「备份 → 修改」**，重跑会毁掉备份；③ 用 Edit 工具做改动
（重复执行会因找不到 old_string 而报错，无害），别用 `cp`+脚本。

## 测量方法（可复用）

`dist/assets/<chunk>.js` 的传递闭包 = 一个窗口真正加载的 JS：
解析 `from"./x.js"` / `import"./x.js"` 递归，累加字节。见提交里的 `_c.mjs` 思路
（临时文件，用完删）。**注意用 Write 工具写脚本，别用 bash heredoc** ——
JS 模板字符串里的 `${...}` 会被 bash 当变量替换掉。
