## 🔴 P0（性能）：主线程被同步命令阻塞 —— 12 个命令里 11 个是同步的

查「主窗口拖拽/滚轮卡顿、插件窗口也卡」。**答案就是用户猜的那个方向**。

**Tauri 把没有 `async` 关键字的命令跑在主线程上**（官方原文：*"Commands without the
async keyword are executed on the main thread unless defined with
`#[tauri::command(async)]`"*），而主线程是给**所有**窗口泵消息的那一条。所以阻塞它
卡的不是一个窗口，是整个应用。

**原本 12 个命令里 11 个是同步的** —— 包括 `plugin_rpc`（每个插件调用都过的网关）。
它背后的服务做的是阻塞文件 I/O：

| 动作 | 主线程上的阻塞 I/O |
|---|---|
| `storage/get` | `create_dir_all` + 读整个 store + JSON 解析（**每次调用，无缓存**） |
| `storage/set` | `create_dir_all` + 整个 store 重写 |
| `host/write_debug_log` | `metadata` + open + write + close，**每行一次** |
| `bus/publish` | `app.emit` 扇出到每一个窗口 |

`plugin_scan` 更重：遍历插件目录 + 读**每个插件的完整入口文件**（算 digest 要字节）——
这就是启动账里 `external 6183ms` 的来源，而且**每次开插件窗口都跑一遍**
（`pluginwin-host.js:163`）。

**有意思的是**：`lib.rs` 里 `plugin_dialog` 的注释**早就写过这个理由**
（"`plugin_rpc` is a *synchronous* command, so it runs on the main thread"），
但当时只是为了躲 `blocking_pick_file` 的死锁，**没有推及全局**。

**改法**：① 12/12 全改 `async fn`，规则统一（不逐条判断"够不够便宜"，因为失败模式
不可见）；② 做 I/O 的命令再套 `spawn_blocking` —— `async` 只把工作挪出主线程，
而阻塞调用会占住 runtime worker，**worker 数 = 核数**，一串 storage 调用会饿死其他
async 任务，那是同一个 bug 换顶帽子。权限闸口留在闭包**外面**。

## 同一轮挖出：自放大的窗口几何回路

`examples/plugins/eyecare/main.js` 胶囊窗口的 `resize` 处理器**每条 `WM_SIZE`** 跑一遍
`reportSize()` + `reportLockRect()`。**Windows 在拖拽/缩放期间是连续发 WM_SIZE 的**，
于是每一遍：

```
getBoundingClientRect() 强制同步布局 → publish（广播到每个窗口）
  → 主窗口 control('size') → plugin_rpc → 原生 SetWindowPos
  → 又产生一个 resize → 回到第一步
```

**跨两个窗口 + 原生侧的自放大回路**，同时占住插件窗口 JS 线程、主线程、所有窗口的
事件处理 —— 主窗口跟着卡，因为其中一样是全局的。

改成 rAF 合并（`scheduleReports`）。**两层保护各管一件事，都要有**：rAF 挡住
"值还在变时跑得比有用更快"，`sizeReporter` 的去重挡住"值停了事件还在来"。
主题变化那条路径原本自带一个 rAF，也并进同一个合并器。

## 排查方法（可复用）

**「谁在阻塞主线程」的查法**：① 列出所有命令，看谁没有 `async`
（`grep -nE "^\s*(async )?fn (plugin_|host_)"`）；② 看这些命令背后的服务有没有
`fs::`；③ 查输入侧有没有按 OS 消息频率跑的 IPC（`resize` / `pointermove`）。

**「日志里 trace 是什么」**：`hub.js` 的 trace 走 **sink → 网关 → `write_debug_log`**，
所以**每条 trace 行本身就是一次主线程 rpc + 一次文件开关**。排查时先看它开没开
（`localStorage['toolbox.traceRpc']`），开着的日志量不能当负载证据。

## ⚠️ git 教训：`git add <具体文件>` 也会带上别处的未提交工作

我 `git add` 时列了 `examples/plugins/eyecare/main.js` —— 它**和它的兄弟一样是未跟踪的**
（`plugin.json`/`idle.c`/`idle.exe`/`README.md` 都还没提交），于是被我一起提交，
结果仓库变成**更糟的半提交状态**：入口提交了、清单没提交 → 新克隆加载不了这个插件。

用 `git reset --soft HEAD~1` + `git restore --staged <那个文件>` + `git commit -C ORIG_HEAD`
修好了。**提交前先 `git status` 看清楚哪些是"别处的未跟踪工作"，别把它卷进自己的提交。**
