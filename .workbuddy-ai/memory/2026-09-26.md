## 剪贴板 / 截屏接口 + 拖放诊断（提交 a3b7a6b）

### 做了什么

- **`ctx.clipboard.{read,write,watch}`**：读/写走 service，**变化**走流提供者 `clipboard`。
- **`ctx.screen.{monitors,capture}`**：`xcap` 截屏，base64 PNG，上限 6400 万像素。

## 第二轮：把「粘贴两遍」的后果追干净

上一轮修了 3 份文档 + `ctx.focusView`。这一轮顺着同一个线索往下查，**范围比想的大得多**。

### 找到并修掉的

1. **`tests/host-kernel.test.mjs` 有两个同名的过时测试**，其中
   `declared hotkeys are registered by the host on the plugin's behalf` 的**后一份断言的是相反的行为**
   （声明即注册），而正确的那份说「声明是请求、不是注册，用户打开才注册」。
   **它靠测试间的状态泄漏才通过**：前一个测试 `setHotkey('hk.plugin','go',{enabled:true})` 留下的
   `store.settings.hotkeys` 不会被 `ls.clear()` 清掉。
   *证明方式*：在该测试里插一行 `store.settings.hotkeys = {}` → 立刻红
   （`the declared hotkey was never registered`）。
2. **`tests/protocol.test.mjs` 有一整段 32 行被粘贴两遍**（4 个测试），
   而两份**中间隔着一个别的测试** —— 所以「找相邻重复块」的做法找不到它。
3. **`tests/file-access.test.mjs`** 有 1 个逐字节重复的测试。
4. **`tests/plugin-interfaces.test.mjs`** 有 2 行重复断言，注释还写着「eight interface checks」（实际 11）。
5. **自检 `t13-registry-views` 的性质写错了**：它要求**每个随仓库发布的**内置插件都注册了视图 ——
   于是用户**合法地关掉**一个内置插件就得到 `view missing: builtin.streamlab/streamlab` 和 14/15。
   正确性质是「每个**运行中**的插件都注册了它声明的视图」，且跳过的要**点名**
   （沿用 t15 的 SKIPPED 约定，让「没验证」和「验证过」可区分）。
   **一个因为用户正确使用产品而变红的检查，会教人忽略整个套件。**
6. **`docs/INTERFACES.md` 的头条计数是错的**：说「9 个命令」，实际 **13** 个
   （`lib.rs` 9 个 + `services/external.rs` 4 个）。连带 §6 的例外表（说插件热键「未实现」，
   而 §8 记着已实现）、§7 的 probe 计数（9→11 项、权限 4→5 个）、§1.2 的磁盘测量（8→10 个插件、896→918 KB）。

### 新增守卫（`tests/docs.test.mjs` → **`tests/hygiene.test.mjs`**，全部注入过违规）

- 文档不许有重复的 `##` 章节（**并直接验提取器本身**）
- **测试文件不许有重复的测试名** ← 这条一上线就抓出上面 5 个
- `INTERFACES.md` 的命令数必须等于源码里的 `#[tauri::command]` 数量（且 §1 表格行数要一致）
- **`lib.rs` 不许对服务名特判**（`svc ==` / `match svc` …）——
  「宿主只查表不特判」是四条硬规则之一，**此前完全没有守卫**。
  正则刻意不匹配 `match services::route(...)`（那是对查表**结果**的 match，是正确的形状）

### 教训

- **`ls.clear()` 不清 `store.settings`** → 测试之间会通过 store 泄漏状态。**依赖什么状态就要清什么状态**，
  否则测试的顺序会决定它是否通过（而且它看起来是绿的）。
- **重复测试名值得当成缺陷**：同名两份里，后一份往往是**过时的旧版本**，断言的是产品已经改掉的行为。
- **「找相邻重复块」会漏掉隔着一段的重复** —— 用「同名声明」去找，而不是用「相邻文本相同」去找。
- **文档里的头条计数没有编译器**。能被代码算出来的数字，就该由测试比对，而不是靠人记得改。

## 第三轮：补齐 `bridge` 的欠账，并因此抓到两个真 bug

`sdk-parity.test.mjs` 把 `files` / `log` / `closeStream` / `ui` 记成「待办」，
这一轮把前三个补上（只剩 `ui`，那是组件工厂，是功能不是镜像）。

### 补上的

- **`bridge.log`**（`console.*` + `[plugin:<id>]` 前缀，同 `ctx.log`；**不写 `debug.log`**）
- **`bridge.files`**（`pick` / `save` / `message`，闸口 `rpc:dialog`，与 `ctx.files` 同形状）
- **`bridge.closeStream`**（无闸，只能关自己开的）
- **所有流创建点都登记句柄**（`stream` / `streamRaw` / `uplink` / `sidecar` / `pty` / `clipboard.watch`）

### 因此抓到的两个真 bug

1. **`bridge.dispose()` 从不释放流** → 关掉插件窗口会留下**跑着的 helper 进程**
   （pty / sidecar），因为**这个窗口是唯一会关它们的东西**（插件的 JS 上下文随窗口一起消失），
   一直到下次启动应用才被 `plugin_reap_orphans` 收掉。
2. **`hub.close` vs `handle.close`**：传输层的 `close()` 只**告诉宿主停**，
   而 hub 自己的注册表（那句 `stream \`id/ch\` is already open` 的判据）**只有 `hub.close` 会清**。
   **等一个终止 `end` 帧来清不是同一件事** —— 帧没到（生产者被杀、宿主被桩掉、teardown 期间关闭），
   槽位就永远占着，插件再也开不了那个 channel id。
   **`ctx` 的 4 处也是这个写法，已一并统一为 `trackStreamClose(ch)`。**

### 我自己引入又被测试抓住的 bug

改 `dispose()` 让它返回 promise 时写成：
```js
const fns = disposer.reverse();   // reverse() 返回【同一个数组】
disposer.length = 0;              // ← 把 fns 也清空了
```
→ **`dispose()` 变成彻底的空操作**。`plugin-bridge.test.mjs` 的第一条测试当场抓住
（「disposed 之后流还在」）。修法是 `[...disposer].reverse()`。
**规律：`arr.reverse()` / `arr.sort()` 原地改并返回同一个数组，先拷贝再清空。**

### 新增测试 `tests/plugin-bridge.test.mjs`（7 条，驱动真实 `makeBridge` + 真实 hub，只桩 `invoke`）

`dispose()` 释放全部流（这就是那个泄漏）；`dispose()` 幂等且对已关闭的流不抛；
`closeStream` 只碰自己的、未知 ch 不触达宿主；**别的窗口的同名 ch 不受影响**；
`files.*` 三个方法都要 `rpc:dialog`（缺权限**快速失败**而不是静默 resolve `[]`）；
取消返回 `[]` / `null` 而不是报错；`log.*` 带插件前缀。

> 为了能测，`makeBridge` 从模块私有改成 `export function makeBridge`。

### 守卫又做对了一次

改完 `bridge` 的接口面，`sdk-parity.test.mjs` **立刻变红**并说清「ctx-only 的集合变了，
要么镜像要么登记」—— 我因此去更新 `SHARED` / `PENDING_CTX_ONLY`，而不是无视它。
**这就是那个守卫存在的意义：让「缺」变成记录在案的决定。**

### 验证

`npm test` **240/240** · `npm run build` ✓ · `cargo check --all-targets` 零警告 · `host-checks` 28/28。

## 第四轮：file drop 一直不生效的真正原因（提交 8095b3f）

用户第二次报告「file drop 仍然不起作用，其他功能正常」。**这次找到了真凶，而且不是插件的问题。**

### 定位过程

我上一轮加的诊断**帮了大忙**——日志明说 drop 是到达的：

```
file drop: enter
file drop: drop
file drop: 1 path(s) → 3 listener(s)
```

三个订阅者（devtool / fileprobe / senses）**全都被调用了**，但什么都没发生。
（顺带发现：trace 是会**丢行**的 —— senses 的 `sub <-` 行在日志里根本不存在，
但它的 `activate` 确实会调 `onDrop`。用探针脚本直接跑 `activate` 证实了这一点。
**不要用 trace 的「没有这一行」当证据。**）

### 根因

`ctx.onDrop` 在**订阅时**快照了插件自己的视图 id 集合：

```js
const mine = new Set(store.views.filter((v) => v.pluginId === id).map((v) => v.viewId));
```

而插件注册视图靠 `ctx.registerView`，**「先接上输入、后面再挂视图」是自然写法** ——
三个插件全都是这么写的（senses 120→127、fileprobe 85→102、devtool 464→983）。
于是订阅那一刻 `mine` 是**空集** → 所有权过滤把**每一个** drop 都拒掉，**一辈子**。

而且**静默**：按设计被拒绝的 drop 和因 bug 被拒绝的 drop，从外面看一模一样。

修法：所有权改成**投递时**判定（`store.views.some(...)`）。

### 为什么上一轮的诊断没抓住它

`delivered` 数的是**被调用的包装函数个数**，不是「有几个插件消费了」。
所以它诚实地报「3 listener(s)」，而那三个全都在第一行 return 了。
**计数类诊断必须说清数的是什么。** 现在日志补上**被路由到哪个视图 + 那个视图属于哪个插件** ——
那才是可行动的信息。

### 为什么旧的测试没抓住它（**第三次同类错误**）

`tests/file-access.test.mjs` 里那条测试**用正则断言了实现**：

```js
assert.match(source, /if \(!payload \|\| !mine\.has\(payload\.viewId\)\) return;/);
```

它把 bug 的形状**钉死成了期望值**，所以功能整个坏掉的期间它一直是绿的。
换成行为测试（订阅在 `registerView` **之前** → 投递 → 断言 handler 真收到），
把旧实现注入回去立刻红。另加源码守卫：不许再出现 `const mine = new Set(`。

> **本仓库已三次栽在「断言写成了只能通过的样子」**：两次是「只匹配旧错误文案」，
> 这次是「正则断言实现细节」。**判据：这条断言在功能完全坏掉时会变红吗？**

### 教训

- **「现在是什么」的判断要在使用时求值，不能在初始化时快照** ——
  尤其当被判断的东西是**之后才会被创建**的（视图、句柄、注册项）。
  快照出来的空集不会报错，它只是让功能永远不发生。
- **计数类诊断要说清数的是什么**（包装函数 ≠ 消费者）。
- **正则断言实现 = 把 bug 钉死成期望值。**
- **trace 会丢行，不能拿「没有这一行」当证据**；要验证插件的 activate 行为，
  直接写探针脚本跑它（单文件 ESM 在 Node 里能直接 import）。

### 验证

`npm test` **241/241** · `npm run build` ✓。宿主侧改动，**插件无需重新部署**。
