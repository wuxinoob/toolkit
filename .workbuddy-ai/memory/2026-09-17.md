## codec 实验：把"用不同方案做实验"落成可复现的数字

原始需求里有一条"用不同方案来做实验"，此前只交付了方案表（7 个 transport ×
codec 组合）和一致性契约，**没有实验结果**。GUI 不可用 → 传输层测不了；但编解码是
纯 JS，在应用内与 Node 下行为完全一致，所以它的单条消息成本是**真实属性而不是
mock 属性**。于是把这一半做成可复现的实验。

**产出**：`bench/codec.mjs` + `npm run bench`。

- **刻意不并入 `npm test`**：时间敏感；CI 里抖动的基准比没有基准更糟。
- 取 7 次运行的**中位数**（均值会被一次 GC 暂停带偏）；先跑预热再计时。
- 明确写清边界：**只测 codec，不含传输**（`invoke` / `Channel` / `emit` 需要活的
  webview）。不写这条的基准会误导人。

### 结果（4 KiB PTY 形状数据块，node v22 x64）

| 路径 | ns/op | 线上体积 |
|---|---|---|
| `json-envelope`（字节数组当 JSON 数字） | 178 982 | 14 660 B |
| `raw-binary` | 1 415 | 4 097 B |
| `rawToEnvelope`（消费者解码路径） | **41** | — |

### 结论（已写入 `docs/PROTOCOL.md` §2）

1. **字节流必须走 raw**：JSON 慢约 126 倍、体积大 3.6 倍 → 这就是 `pty-stream`
   选 `raw-binary` 的实测依据，不再是"显然如此"。
2. **raw 解码几乎免费（41 ns）**：它返回 `subarray` **视图**而不是拷贝，成本在
   **产出侧**（分配+拷贝）。所以即使帧率很高，消费者侧依然便宜。
3. **`line-json` 并不免费**：小帧比 `json-envelope` 贵 25%，1 KB 文档贵 60%
   （同一个 codec 再加换行与去尾换行）。它存在是因为 sidecar 管道**需要分隔符**，
   不是因为便宜。
4. **小控制帧用 raw-binary 反而贵约 20%**（字段逐个处理，没有 JSON 快路径），
   但它根本装不下嵌套对象 —— 对控制消息这是**能力边界而非取舍**。

一句话：方案表编码的是一个真实取舍 —— 自描述的控制/事件走 JSON，字节流走 raw。
现在是**量出来的**。
